# Rust 전환 실험 기록

작성일: 2026-11-06 · 브랜치: `experiment/rust-core-refactor` · 기준: `c60d975`

## 현재 결론 — 부분 채택 후속 실험

사용자 요청에 따라 모듈의 개선과 전면 전환을 분리해 다시 판단했다. **활동 파서와 섹션
개요 파서는 실험 브랜치의 명시적 실행 경로에 부분 채택**했다. 개념 우선순위 계산은
현재 JSON/FFI 경로가 느려 채택하지 않았고, 내부 웹도 실제 API를 측정해 검토 범위에 넣었다.
기본 Python 진입점과 운영 `turtleneck`은 그대로다. 아래 1차 원시 수치는 보존한다.

최신 결과와 실행 방법은 [부분 채택 후속 기록](RUST_PARTIAL_RESULTS.md), 요약은
[부분 채택 보고 메모](RUST_PARTIAL_REPORT_MEMO.md)를 기준으로 한다.

## 1차 당시 결론과 goal 처리

**활동 파서는 빨라졌지만 대표 동기화 전체 흐름의 개선이 없어 확대 전환을 중단했다.**
기존 `turtleneck`과 운영 Python 구현은 보존했다. Rust 시제품·재현 가능한 비교·회귀 검사·
판정 도구를 실험 브랜치에 남기며 원격 푸시는 하지 않는다. 기존 9단계 HTML 조건부 요청은
사용자 요청에 따라 폐기한 상태이며 이번 실험과 연결하지 않는다.

측정 전에 고정한 조건은 [PLAN.md](../../../experiments/rust-core/PLAN.md)에 있다. 활동 목록 파서의
출력·오류·URL·제한 문구가 같아야 하며, 대표 목록 확인과 전체 메타데이터 동기화가 **각각
중앙값 20% 이상 단축**되고 95% 반복측정 구간도 개선 방향이어야 다음 전환을 허용한다.
1차 [decision.json](../../../experiments/rust-core/results/decision.json)의 `allow_expansion`은 false다.
이는 전면 확대용 기존 기준이며, 후속 부분 채택은 별도 `partial-decision.json`으로 판단한다.

## 구현 범위

- 기존 `_ActivityParser`의 활동 링크·제목·본문·종류 추출을 Rust 토크나이저로 구현했다.
- 같은 프로세스에서 C ABI로 호출한다. 비교 시간에는 UTF-8 인코딩, FFI, Rust 파싱·JSON
  직렬화, Python JSON 복원과 필요한 Python 복구 비용을 모두 포함한다.
- 잘못된 마크업의 복구 규칙이나 중복 속성은 두 파서가 다를 수 있어 Python으로 되돌린다.
  URL 속성의 원래 CR/LF와 Unicode도 보존한다. 원래 URL을 조용히 정규화하지 않는다.
- 공유 provider 지점에 실험용 어댑터를 연결해 회귀 검사했다. 로그인·쿠키·요청 간격·권한·
  DB 스키마·기존 운영 모듈은 전환하지 않았다. 빌드 결과물은 Git에서 제외한다.

## 시간 비교

Release 빌드, Python 3.11.9, Windows x64 GNU 환경에서 30쌍씩 순서를 번갈아 측정했다.
작은 입력은 한 표본에서 여러 번 실행하고 1회당 시간으로 환산했다. 테스트 입력 준비,
임시 DB 복사와 결과 검사는 타이머 밖이다. 원시 표본·p95·CPU 표본·쌍별 부트스트랩 구간은
[benchmark.json](../../../experiments/rust-core/results/benchmark.json)에 있다.

| 조건 | Python 중앙값 | Rust 경로 중앙값 | 시간 단축 |
| --- | ---: | ---: | ---: |
| 활동 10개 파싱 | 0.146 ms | 0.031 ms | 78.99% |
| 활동 100개 파싱 | 1.344 ms | 0.255 ms | 81.00% |
| 활동 1,000개 파싱 | 13.811 ms | 2.564 ms | 81.44% |
| 활동 100개 전체 지문 계산 | 3.288 ms | 2.058 ms | 37.43% |
| **변경 없는 목록 동기화 재현 전체** | **210.468 ms** | **210.824 ms** | **개선 없음** |
| **전체 메타데이터 동기화 재현** | **1,135.452 ms** | **1,136.691 ms** | **개선 없음** |

동기화는 8과목 고정 HTTP 응답과 동일 초기 DB를 사용했다. 전후 요청 수와 매 표본의 저장
학업 정보가 일치했다. 재현에는 실제 네트워크 지연이 없으므로 서비스 전체 속도로 해석하지
않는다. 단독 파서의 큰 개선율을 전체 실행 시간 감소율로 확대하지 않는다.

대표 목록 확인의 단축률은 -0.169%, 95% 구간 **[-0.814%, +0.683%]**였다. 전체 수집은
-0.109%, **[-0.830%, +0.175%]**였다. 모두 0을 포함하고 사전 20% 기준에 크게 못 미친다.
Rust가 확실히 느려졌다고 판단할 근거도 없으며, 현재 측정에서는 사실상 같은 시간이다.

## 실제 TLS HTML 검증

학교에서 실제 9과목의 HTML을 한 번 읽어 메모리 안에서만 보관했다. 입력은 압축 해제 후
UTF-8 기준 **607,188 B**, 활동 **182개**였다. 모든 추출 결과가 같았고 복구가 필요한
페이지는 0개였다. 저장된 HTML·URL·과목 ID·계정·쿠키는 없다.

9과목 활동 파싱만 30쌍 비교하면 **34.336→10.945 ms, 68.13% 단축**이었다. 95% 단축 구간은
**[67.881%, 68.716%]**다. 약 23.391 ms의 로컬 처리 절약이며 실제 TLS 동기화 완료 시간이
68% 줄었다는 뜻이 아니다. 인증·HTML 준비 요청 15회는 이 타이머에서 제외했고 기존 요청
간격을 유지했다. 원본 사용자 DB나 학교 데이터를 수정하지 않았다.

## 메모리와 초기화

새 Python 프로세스 3개씩에서 같은 활동 1,000개를 30회 파싱한 후 최대 working set을 읽었다.
중앙값은 Python **37.29 MB**, Rust 경로 **39.03 MB**로, Rust 쪽이 약 **1.74 MB 증가**했다.
MB는 1,000,000바이트다. Windows process working set이며 Python 객체만의 메모리나
OS 공통의 정확한 private allocation 지표로 해석하지 않는다.

추가 Rust DLL 초기화 중앙값은 약 **0.790 ms**였다. 자식 테스트 프로세스의 전체 시간에는
30회 파싱이 포함되므로 애플리케이션 시작 시간으로 비교하지 않는다. Windows CPU 시간은
짧은 구간에서 분해능이 거칠어 CPU 표본을 세부 개선율 근거로 삼지 않았다.

## 검증 결과

- Rust 단위 검사 **3개 통과**: 중첩·엔티티·중복 속성·ABI 입력·메모리 반환.
- Python/Rust 어댑터 검사 **6개 통과**: 정적 20개·생성 200개·동시 100개 입력,
  Unicode·중복 속성·URL 줄바꿈·분할 입력·잘못된 UTF-8·입력 상한.
- 기존 대학 기능 **368개 중 366개 통과·2개 건너뜀**, 서버 **16개 모두 통과**.
  provider 연결 지점에서 native 파서가 **1,030회** 실행됐고 이 회귀 검사 입력의 복구는 0회다.
  하위 Python 프로세스는 기존 Python 경로를 유지한다. 모든 subprocess가 Rust였다는 뜻이 아니다.
- 확대 판정 검사 **5개 통과**: 필요한 흐름·회귀 증거 누락, 요청/결과 불일치, 개선 부족,
  0을 포함하는 반복 측정 구간이 확대를 막고, 완전한 통과 근거일 때만 다음 단계를 허용한다.
- 기존 회귀 382개와 추가 14개 검사가 통과했다. 건너뛴 2개는 기존의 macOS PDFKit·선택적 PDF
  추출 의존성 검사다.

## 다음 전환을 위한 구성

[재현 안내](../../../experiments/rust-core/README.md)에 빌드·동등성·provider 회귀·반복 측정 명령을
정리했다. `assess.py`는 필수 흐름 누락, 회귀 실패, 출력 불일치 또는 성능 기준 미달이면
확대를 허용하지 않는다. 단독 마이크로벤치마크만 통과해도 확대하지 않는다.

향후 대표 입력이 크게 바뀌거나 파싱이 주된 비용이라는 새 측정이 생겨 기준을 통과하면
section overview → course structure → visible-text normalization 순서의 후보를 하나씩
옮기고 같은 판정을 반복한다. 현재 결과로 이 나머지 전환을 수행하면 검증·빌드 부담이
추가되는 데 비해 전체 실행 이득이 확인되지 않는다.

현재 한계: Windows x64에서만 빌드·실행했으며 macOS/Linux·서명된 배포 번들·전체 앱 시작
시간은 검증하지 않았다. 전체 메모리 절감이나 학교 서버 부하 감소도 주장하지 않는다.
