# 문제 생성 다음 최적화 계획

2026-11-06 · 기준 커밋 `4e248f9` · 방안 도출/읽기 전용 진단 단계

후속 실행: [1·2단계 상세 결과](STUDY_GENERATION_NEXT_OPTIMIZATION_RESULTS.md),
[보고 메모](STUDY_GENERATION_NEXT_OPTIMIZATION_REPORT_MEMO.md).
CLI 입력 크기는 줄었지만 실자료 관측은 81.2초로 60초 목표 미달이다.
아래는 실행 전 계획으로 보존한다. 3·4단계는 미구현이다.

이후 네 가지 실행 결과: [상세](STUDY_GENERATION_REMAINING_RESULTS.md),
[보고](STUDY_GENERATION_REMAINING_REPORT_MEMO.md). 부족분/자료 준비는 구현했고 병렬은
실험·교차검토 후 기본 미채택했다. 위 미구현 문장은 이전 시점의 상태다.

## 결론

다음 구현은 **호스트 입력 중복 제거 → 생성 데이터만 작성하는 제출 흐름 고정 → 재측정**
순서가 적절하다. 재생성에는 기존 개념 분석과 후보를 보존하고 부족분만 생성하는 방식을
이어 적용한다. 새 자료 30문항이 계속 60초를 넘으면 호스트가 실제 지원하는 병렬 생성도
별도 실험으로 검토한다. Python 연산/Rust 포팅은 이번 시간 목표의 우선 병목이 아니다.

이 문서는 구현 승인이 아니라 후보와 검증 순서다. 이번 작업은 운영 코드를 바꾸거나
원격에 푸시하지 않았다. 기존 결과 문서의 '원격 미반영'은 당시 상태다. 기준 커밋은 이후
`origin/turtleneck`에도 푸시됐지만, 설치 플러그인/원래 체크아웃은 자동 갱신되지 않았다.

## 1. 근거와 필요한 개선 폭

실제 Java2 30문항의 HTTP API 준비는 69.886초였다. 이 실행에서 세 로컬 호출의 합은
0.424초다. 이 호출 시간을 전부 없애도 산술적으로 69.462초가 남는다. 나머지는 호스트의
분석·문항 작성·검토·스크립트 작성, 도구 왕복과 서버 준비 등이 합쳐진 시간이다. 이를
순수 모델 추론 시간이나 CPU 사용률로 부르지 않는다.

| 전체 준비 목표 | 현재 관측치에서 더 줄여야 할 시간 | 필요한 단축 비율 |
| --- | ---: | ---: |
| 60초 | 9.886초 | 14.15% |
| 45초 | 24.886초 | 35.61% |
| 30초 | 39.886초 | 57.07% |

이는 목표 차이 계산이며 다음 변경의 예상 효과가 아니다. 단일 실측은 같은 대화에서 이미
자료를 읽은 상태였으므로, 처음 보는 자료의 반복 성능을 대표하지 않는다.

## 2. 실행 순서

### 0단계 — 적용 경로와 비교 조건 고정

- 실제 사용하는 Codex 스킬/CLI/번들의 경로와 소스 버전을 확인한다. `packaging/turtleneck_cli.py`는
  소스 실행이면 그 파일의 상위 저장소, 번들이면 `_MEIPASS` 안의 skill을 실행한다.
  GitHub 푸시만으로 실행 중인 설치본이 바뀌었다고 판단하지 않는다.
- 동일 PDF 해시, 30문항, 유형·난이도·선택지 수, 같은 호스트 조건을 고정한다. 신규 분석,
  같은 분석 재사용, 설정을 바꾼 재생성을 별도 시나리오로 둔다.
- 요청/본문 준비 → 호스트 전달 → 추출 결과 검증 → 조합 → HTTP 준비 → 화면 표시를 구분한다.
  호스트가 노출하지 않는 토큰 수·첫 토큰 지연·순수 추론 시간은 추정해서 채우지 않는다.
- 이전/이후를 교대 순서로 최소 5쌍 탐색 비교한다. 효과가 보이면 10쌍 이상으로 늘려 중앙값과
  모든 원시 표본을 남긴다. 적은 실사용 표본의 p95는 안정적인 운영 지표라고 주장하지 않는다.

### 1단계 — 첫 SOURCE와 공통 설명의 중복 전송 제거

현재 `_open_batch()`는 첫 요청 전체를 `hostOnly` 루트에 넣고, 동일 요청을 다시
`hostOnly.requests[0]`에 넣는다. 원문뿐 아니라 instruction/schema/settings도 중복된다.
새 전달 형식은 requests를 유일한 요청 목록으로 사용하고 묶음 ID만 바깥에 둔다.
묶음 내 공통 instruction/schema를 공유하는 추가 변경은 첫 중복 제거를 측정한 뒤 판단한다.

**크기만 확인한 제안 실험**: 실제 PDF가 아닌 합성 본문을 기존 코드로 준비하고, 반환 JSON의
루트 중복만 제거한 복사본을 비교했다. 모든 requests의 SOURCE가 동일함을 assert했다.

| 합성 본문 | 묶음 요청 수 | 현재 → 제안 JSON | 바이트 감소 |
| --- | ---: | ---: | ---: |
| 7,703자 | 1 | 58,566 → 29,504바이트 | 49.62% |
| 20,000자 | 2 | 125,979 → 72,134바이트 | 42.74% |

**토큰이나 실제 생성 시간이 이 비율로 줄어든다는 뜻은 아니다.** 원문 중복을 없애도 출력 생성이
지배적이면 시간 효과는 작을 수 있다. 루트 SOURCE를 읽는 기존 호출자/테스트/스킬 계약을
확인하고 버전별 호환 경로 또는 명시적인 일괄 이행이 필요하다. sourceIndex는 각 request 안의
SOURCE를 계속 가리켜야 하며 이미지 ref·권한·인용 검증을 보존한다.

도달 범위: `study_pipeline._open_batch`, 호스트의 요청 소비 방식, SKILL/`references/study.md`,
CLI 반환 계약과 관련 테스트. 제안 복사본은 실제 실행기로 적용하지 않았다.

### 2단계 — 매 시험의 Python 작성 대신 compact JSON 제출을 기본 작업으로 고정

실제 테스트는 호스트가 매번 별도 Python 작성 스크립트를 만들어 공통 필드를 조립했다.
현재 `--event-file`과 compact 형식이 이미 있으므로, 고정된 제출 흐름으로 **문항 데이터만**
작성하고 정상 이벤트로 전달한다. 기존 도구가 파일 쓰기와 이벤트 호출을 지원하면 이를
재사용하고, 매 시험 새로운 실행 코드를 생성하지 않는다. 반복 문자열을 줄이기 위한 별도
축약 언어/임의 코드 실행 기능은 추가하지 않는다.

동일 유형에 필요 없는 schema 안내도 전달 전에 줄일 수 있다. 객관식은 이미 줄였으므로
나머지 유형은 실제 요청이 있을 때만 검토한다. 다형식 auto에서는 필요한 코드·정답·채점
조건을 잘못 없애지 않도록 유형별 계약을 유지한다. 해설·근거를 삭제해서 빠르게 만들지 않는다.

기대 효과는 호스트의 코드 작성·수정·포맷 복구 작업 감소다. 실제 절감 시간은 미측정이다.
기존 `questionDefaults`, `answerIndex`, `sourceIndex`를 먼저 사용하고 alias를 계속 늘리지 않는다.

**여기까지 적용 후 0단계 조건으로 다시 측정한다. 60초 이내가 반복 확인되면 신규 생성
최적화 확대를 멈추고 품질/실사용 적용 확인으로 넘어간다.**

### 3단계 — 재생성은 기존 개념·후보를 보존하고 부족분만 생성

현재 같은 분석의 재사용은 이미 있다. 단순히 캐시를 추가하는 것은 새 방안이 아니다.
하지만 `analysis_key()`에는 난이도·유형·선택지 수가 포함돼 있고, 후보 예산이 부족하면
`reuse_analysis()`가 false를 반환해 해당 파일의 분석까지 다시 할 수 있다.

원문·범위가 같은 경우 개념/근거와 문항 조건을 분리하고, 현재 조건을 만족하는 후보를
먼저 고른 뒤 부족한 개수/유형만 추가 생성한다. 난이도가 바뀌면 기존 문항을 그대로
쓸 수 있다고 가정하지 않고 새 문항을 만들되, 유효한 원문 분석까지 반복하지 않게 한다.
현재 권한, 사용자, 본문 해시, 위치 범위, 추출 버전과 분석에 영향을 주는 참고 조건은
반드시 재검사한다. 금지 자료나 다른 사용자의 분석을 캐시에서 복원하지 않는다.

대상은 '같은 파일로 문항 수/유형/난이도를 바꾸는 요청'이다. 처음 보는 PDF 30문항을
빨리 만드는 효과로 보고하지 않는다. 부분 실패/중복/재시도와 기존 분석 기록 보존이
필요해 1·2단계보다 구현 위험이 크다.

### 4단계 — 여전히 느리면 호스트 병렬 생성 실험

호스트가 실제 독립 병렬 작업을 지원할 때만 30문항을 개념 범위가 겹치지 않는 15+15로
나눠 실험한다. Python 스레드를 늘리거나 requests를 두 개 반환하는 것만으로 LLM 생성이
병렬화되지는 않는다. 이번 방안 도출에서 하위 에이전트를 실행하지 않았다.

각 작업의 출처와 요청 ID를 보존하고, 결과를 단계적으로 수집한 뒤 저장·최종 검토는
기존 계약을 유지한다. 전역 중복과 문항 간 정답 노출도 다시 검사한다. 생성 시간이
줄어도 입력 중복·호스트 비용·합치기/재검토 시간이 늘 수 있으므로 전체 완료 시간으로
판정한다. 새 API 키/모델 SDK를 도입하는 별도 서비스 전환은 이 단계의 전제가 아니다.

## 3. 파일 준비 경로는 별도로 개선

TLS `--ensure --resource-id`는 파일 요청을 좁히면서도 변경/TTL 조건에 따라 다른 과목의
학업·공지·자료를 확인한다. 자바2 테스트의 준비 시간은 80.907초/291요청이었다.

생성 전 이미 허용된 로컬 원본과 분석을 사용할 수 있으면 불필요한 전체 동기화를 끼우지 않는다.
새 파일 요청에는 대상 과목/자료의 현재 제한을 확인하는 좁은 준비 경로를 검토한다.
다른 과목 갱신을 제외하더라도 수강 여부·자료/공지 제한과 실패 시 보존은 유지한다.
학사 조회 명령의 freshness 계약은 별도로 유지한다. 생성 69.9초와 준비 80.9초의 개선을
합쳐서 같은 지표처럼 보고하지 않는다.

## 4. 채택 기준과 기록

- 신규 자료 30문항의 기본 목표는 전체 HTTP 준비 중앙값 60초 이하, 확장 목표는 45초다.
  화면 표시까지 확인하면 그 지연도 별도로 기록한다. 첫 10문항만 표시한 시간으로 대신하지 않는다.
- 문항 수·유형·정답·원문 근거·코드 조건·출처 접근 검사를 유지한다. 형식 검사는 기존 회귀,
  의미·정답·중복·오답 선택지 품질은 호스트가 검토하고 실제 실패/수정 내역을 기록한다.
- 구조적 파싱의 등가성, 본문 누락/중복 없음, 잘못된 sourceIndex, 구버전 요청, 부분 재시도,
  권한 철회와 사용자 분리까지 해당 변경에 맞춰 검사한다.
- 효과가 없으면 되돌린다. 바이트 감소율·호스트 대기 감소·전체 준비 시간을 각각 보고한다.
