# 남은 네 가지 최적화 실행 기록

2026-11-06 · 기준 `50ce63c` · 로컬 `turtleneck` · 이번 변경 미푸시

## 결론

네 항목을 수행했다. **부족분 재생성**과 **대상 자료만 준비하는 경로**는 구현·검증했다.
같은 자료/문항 조건의 호스트 생성도 직렬 5회·병렬 5회 비교했다. 병렬의 생성 구간은 짧았지만
최종 검토에서 품질 문제가 발견되어 **기본 병렬 경로는 채택하지 않았다.** 신규 자료의
30문항 전체 준비를 30~60초에 완료했다는 판정은 하지 않는다.

| 항목 | 실행 결과 | 판정 |
| --- | --- | --- |
| 조건을 맞춘 반복 비교 | 같은 PDF/30객관식/4선택지/기본 난이도로 직렬·병렬 각 5회 | 생성 단계 비교, 전체 지연과 구분 |
| 부족분만 추가 생성 | 10개 보유 → 30개 요청의 새 후보 예산 36→20개 | 구현, 기존 10개 유지 |
| 실제 호스트 병렬 실험 | 생성 구간 중앙값 71.306→42.018초 | 품질/전체 지연 조건 미충족, 기본 미채택 |
| 좁은 자료 준비 | 같은 8과목 fixture 요청 98→8회; 실제 Java2 7회·2.234초 | 구현, 권한/수강 확인 유지 |

## 1. 같은 조건의 실제 호스트 반복 비교

허용된 Java2 '제네릭과 컬렉션A' PDF의 추출 텍스트를 사용했다. 24쪽·7,703자,
SHA-256 `731777542322dd4fd3f49928dbec711442d9978d4d0d891bc02a7066beba428d`.
모든 실행은 객관식 30문항, 선택지 4개, 기본 난이도, 짧은 문항별 해설과 정확한 인용이다.
1~10쪽에서 15개, 11~24쪽에서 15개를 만들도록 범위를 고정했다. 새로운 Python 작성
스크립트나 결정적 재생 결과를 AI 생성으로 세지 않고 호스트가 매번 JSON을 직접 작성했다.

직렬은 한 작업자가 30개, 병렬은 두 작업자가 각각 15개를 작성했다. 병렬 매 회차는
준비 장벽으로 시작을 맞추고 `두 종료 중 늦은 시각 - 두 시작 중 이른 시각`으로 계산했다.
각 작업자의 자체 검토와 형식/정답 구조/인용 검사는 해당 작업자의 시간에 포함했다.

| 회차 | 직렬 30개 | 병렬 15+15개의 벽시계 시간 |
| --- | ---: | ---: |
| 1 | 70.780초 | 42.018초 |
| 2 | 71.306초 | 40.797초 |
| 3 | 70.906초 | 42.356초 |
| 4 | 71.704초 | 43.522초 |
| 5 | 74.052초 | 40.682초 |
| 중앙값 | **71.306초** | **42.018초** |

이 표의 생성 구간 중앙값 차이는 약 **41.07%**다. 그러나 첫 원문 읽기/작업자 시작,
부모의 전체 교차검토·수정·조합·웹 시작은 제외했다. 직렬 5회를 먼저, 병렬 5회를 나중에
실행했으며 교대 무작위 순서가 아니다. 문항 내용·실제 출력 토큰량도 같지 않다. 같은
상위 호스트 모델 구성을 상속했지만 백엔드 버전·큐·순수 추론 시간은 노출되지 않았다.
따라서 전체 시험 준비가 41% 빨라졌다는 결론이나 60초 목표 달성 근거로 사용하지 않는다.

### 교차검토 결과와 미채택 이유

별도 호스트 작업자가 병렬 결과 5세트·150문항을 원문과 다시 비교했다. 형식/정확한
인용은 전부 통과했고 이 검토에서 잘못된 정답 키는 발견하지 못했다. 다만 다음 문제가 있었다.

- 의미 중복 1쌍: 5회차에서 push의 인자 타입을 두 번 물었다.
- 다른 문항의 답을 드러내는 명확한 단서 3쌍: 일부 문항의 질문 자체가 다른 문항의 값을 밝혔다.
- 5회 모두 정답 위치가 0→1→2→3 순서로 반복됐다. 직렬 초안에도 같은 규칙성이 있어
  이를 병렬 방식만의 문제라고 주장하지 않는다.
- 5세트 전체 교차검토에는 **150.522초**가 추가로 들었다. 이 일괄 검토 시간을 5로 나눈
  값을 개별 시험의 실제 지연으로 간주하거나 생성 시간에 임의로 더해 전체 시간을 만들지 않는다.

문항은 이 실험에서 수정하지 않았다. 검토·교체까지 끝난 동등 품질의 전체 지연이 없으므로
병렬을 기본 실행에 넣지 않았다. 형식 통과는 교육적 정확성/독립성을 보장하지 않는다.
직접 Java 실행, PDF 이미지 판독, 교사의 독립 평가와 학습자 평가는 하지 않았다.

[원시 시간·해시·집계된 품질 문제](../../../experiments/study-generation/results/remaining/parallel-experiment.json).
원문·생성 문항·상세 검토는 Git 바깥 비공개 작업 폴더에 보관한다.

## 2. 부족분만 추가 생성

이전에는 후보가 모자라면 해당 파일의 캐시 재사용이 실패해 분석과 전체 후보 생성을 다시
요청할 수 있었다. 현재는 다음 경로를 사용한다.

1. 현재 자료 접근/본문/범위를 확인한다. 호환되는 기존 후보와 분석 단위를 가져온다.
2. 모든 자료의 기존 은행으로 요청을 채울 수 있으면 그대로 재사용한다. 그 외에는 파일별
   분담 기준의 부족 슬롯을 배분한다. 여러 파일·혼합 유형에서 전역 최소 생성량은 보장하지 않는다.
3. `reusedAnalysis`와 `existingQuestions`를 전달한다. 호스트는 개념/맥락을 다시 작성하지
   않고 새로운 questions/types와 필요한 shortageReason만 제출한다.
4. 저장된 원문 분석을 복원하여 인용/형식/유형을 재검증하고 기존 후보 뒤에 추가한다.
   같은 요청을 중단/재개할 수 있고, 모든 결과가 검증되기 전에는 해당 묶음을 저장하지 않는다.

난이도·유형·선택지 수가 바뀌면 예전 문항은 가져오지 않는다. 별도의 원문 분석 캐시에서
개념·설명·근거만 재사용하고 새 조건의 문항을 요청한다. 사용자·과목·본문 해시·위치·참고
조건을 분리하고, 자료 금지/본문 변경/명시적 rebuildAnalysis는 재사용을 막는다. 원문 분석
캐시는 출처별 중요도 판정을 새 조건에 그대로 옮기는 용도로 쓰지 않는다. 현재 자료의
정답·근거와 최종 문항 간 중복은 호스트가 다시 검토해야 한다.

같은 fixture로 30회 비교한 결과:

| 10문항 보유 후 30문항 요청 | 기준 코드 | 변경 코드 |
| --- | ---: | ---: |
| 새로 요청한 후보 예산 | 36개 | **20개** |
| 기존 후보 유지 | 새 은행에서 사용하지 않음 | **10개 유지** |
| 최종 문항 수 | 30개 | **30개** |
| 원문 분석 재사용 | 요청에서 재분석 | 재사용 |
| 준비 요청의 로컬 중앙값 | 12.324ms | 9.326ms |

추가 후보 요청량은 44.44% 줄었다. 이는 실제 모델의 생성 시간 감소율이 아니다. fixture
문항은 상태/보존 검사용이며 의미적 교육 품질이나 실제 AI 지연을 측정하지 않는다. 두 버전의
오프라인 표본 수는 각각 30개이며 교대 실행이 아니고 다른 검사와 겹쳐 로컬 ms를 엄밀한 지연 A/B로
주장하지 않는다. 요청 개수/보존/결과의 검증을 주된 근거로 삼았다.

## 3. 대상 자료 준비

새 옵션: `sync_tls.py --resource-only --resource-id <이미 확인한 ID>`.
여러 자료는 --resource-id를 반복해 한 호출에 모은다. 해당 ID가 같은 연결 범위의 로컬
목록에 있어야 하며, 현재 수강 목록과 대상 과목의 최신 공지·자료 제한을 확인한다.

- 다른 과목의 과제·미시청 강의·공지·자료 전체를 갱신하지 않는다.
- 전체 목록/학사 상태의 성공 시각은 갱신하지 않고 대상 파일 확인만 기록한다.
- 모르는 ID/연결 범위 변경/수강 철회는 실패한다. 현재 목록에서 사라진 대상은 접근을 막는다.
- 파일 확인 오류는 이전 자료와 성공 확인 시각을 보존하고 실패로 보고한다.
- 기존 --ensure/전체 새로고침/학사 조회 계약과 학교 요청 제한·재시도는 유지한다.

같은 8과목 초기 DB, 같은 HTTP 응답, 만료된 확인 시각, 같은 파일 하나 요청을 각각 30회
재현했다. 기존 --ensure --resource-id와 새 --resource-only --resource-id를 비교했다.
두 경로 모두 같은 파일 하나를 준비했고 과제/강의의 값은 같았다.

| 오프라인 재현 | 기존 | 대상 자료 경로 |
| --- | ---: | ---: |
| HTTP 요청 수 | 98회 | **8회** |
| 로컬 재현 중앙값 | 1,219.652ms | 81.994ms |

요청 수는 **91.84% 감소**했다. HTTP 재현에는 실제 통신 지연/학교 요청 간격을 넣지 않았으므로
ms 차이를 실제 학교 시간 단축률로 보고하지 않는다.

실제 Java2 지정 자료의 새 경로도 실행했다: **2.234초, 7회 요청**, 본문 응답 46,172바이트.
파일 요청 1회는 **304 재검증**이어서 새 파일 본문은 전송하지 않았다. 이전 80.907초/291요청은
전체 메타데이터와 파일 본문 전송까지 포함해 조건이 다르다. 둘의 차이를 순수 옵션 효과로
계산하지 않는다. 학교에 쓰기/제출하지 않았으며 기존 보호된 연결을 재사용했다.

## 검증·재현·한계

부족분 보존, 유형 변경, 원문 변경, 강제 재분석, 중단/오류 재시도, 권한 철회, 특정 자료의
금지/삭제/수강 철회/미등록 ID/네트워크 오류, 전체 freshness 보존을 검사했다. 기존 회귀와
서버 검사 결과는 [regression.json](../../../experiments/study-generation/results/remaining/regression.json)과
[로그](../../../experiments/study-generation/results/remaining/regression.txt)에 따로 저장했다.

최종 전체 검사: 대학 기능 391개 중 **390개 통과·1개 건너뜀**, 서버 **16개 통과**.
총 **406개 통과**, 오류/실패 0개다. 건너뛴 검사는 선택적 환경 의존 검사다.

```powershell
$env:PYTHONUTF8='1'
python experiments/study-generation/remaining_benchmark.py --narrow --output experiments/study-generation/results/remaining/after.json
python experiments/study-generation/verify.py --output-dir experiments/study-generation/results/remaining
```

기준 재현은 `50ce63c`의 별도 체크아웃을 --source-root로 지정하고 --narrow를 빼서 수행한다.
단계별 기존 실측 파일은 덮어쓰지 않았다. 전체 신규 시험 30~60초, 코드 실행 기반 정답 확인,
다른 OS, 설치된 플러그인의 자동 갱신은 아직 검증/실행하지 않았다. 이번 결과를 신규 생성
목표 달성으로 합산하지 않는다.

이전 캐시에 원문 분석의 참고 조건을 확인할 메타데이터가 없으면 새 조건의 사실 캐시로
재분류하지 않는다. 기존 호환 문항은 보존할 수 있지만, 유형 변경에는 한 번의 새 분석이
필요할 수 있다. 다파일 혼합 유형의 전체 은행이 이미 요청을 채우는 경우에는 파일별 유형
할당 때문에 불필요하게 생성하지 않는 별도 회귀를 확인했다.
