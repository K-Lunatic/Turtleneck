# 후속 최적화 1·2단계 실행 기록

2026-11-06 · 로컬 `turtleneck` · 기준 `4e248f9` · 이번 변경 미푸시

## 판정

**CLI 입력 중복은 줄였다. 실제 생성 시간 개선은 입증하지 못했다.** Java2 실자료의 새 실행은
30문항·HTTP API 준비까지 **81.232초**였다. 이전 69.886초 관측보다 길어 60초 목표는 미달이다.
두 실행은 문항·출력량·실행 경로가 달라 인과적인 가속/회귀율을 계산하지 않는다.

이번에는 1단계 입력 중복 제거와 2단계 기존 JSON 제출 흐름 고정을 수행했다. 부족분만
재생성하는 캐시 개편과 호스트 병렬 생성은 구현하지 않았다. 새 API/모델/의존성도 추가하지 않았다.

## 변경과 적용 범위

1. `study_pipeline.host_response()`에서 추출 요청의 첫 부분 복사본을 제거한다. 실제
   `run_agent.py` CLI는 `handoffVersion: 2`와 `hostOnly.requests`를 반환한다. 각 SOURCE와
   schema/settings/instruction은 해당 request 안에 한 번 들어 있다. 전체 문서와 이미지 ref는
   그대로 보존하며 request/batch ID와 sourceIndex 의미도 같다.
2. 직접 Python으로 `StudySession.call()`을 호출하면 기존 루트 SOURCE를 포함한 반환을
   유지한다. 개념 설명의 needsGeneration, 일반 조회, 조합·채점 응답도 변경하지 않는다.
   CLI를 직접 파싱하던 외부 소비자는 `hostOnly.requests`로 이행해야 한다.
3. SKILL과 학습 계약에 compact JSON을 파일에 직접 쓰고 기존 `study --event-file`로 제출하도록
   명시했다. 매 시험 Python 작성 스크립트를 생성하는 작업을 없앤다. 문항별 해설·개념·근거와
   최종 중복/정답 노출 검토는 유지한다. 새 제출 명령이나 축약 언어는 만들지 않았다.

자동 설치/업데이트는 하지 않았다. 현재 CLI와 해당 SKILL을 사용하는 경로에 적용되며,
예전 스킬이 루트 SOURCE를 기대하면 현재 CLI와 조합해 사용할 수 없다.

## 동일 요청의 전달 크기

합성 본문을 기존 StudySession으로 준비하고 동일 객체에 실제 `host_response()`를 적용했다.
모든 요청의 SOURCE와 메타데이터가 같고 원본 응답이 바뀌지 않음을 검사했다.
비밀 정보 제거와 UTF-8 JSON 직렬화를 포함해 30회 교대 순서로 측정했다.

| 합성 본문 | 요청 수 | 기존 반환 → CLI v2 | 바이트 감소 |
| --- | ---: | ---: | ---: |
| 7,703자 | 1 | 58,566 → 29,523바이트 | 49.59% |
| 20,000자 | 2 | 125,979 → 72,153바이트 | 42.73% |

7,703자 경우 비밀 정보 제거·직렬화 중앙값은 0.802→0.417ms였다. 이 수 ms 이하의 변화는
실사용 전체 단축으로 일반화하지 않는다. 바이트 감소율도 모델 토큰/시간 감소율이 아니다.
[원시 표본](../../../experiments/study-generation/results/handoff-step12.json).

## 실제 Java2 CLI 관측

이전과 같은 '제네릭과 컬렉션A' PDF: 24쪽, 추출 텍스트 7,703자,
SHA-256 `731777542322dd4fd3f49928dbec711442d9978d4d0d891bc02a7066beba428d`.
사용자가 허용한 로컬 원본의 복사본과 별도 학습 DB에서 시험했다. 학교에 다시 접속하거나
원래 학습 기록을 바꾸지 않았다. 이미 본 자료가 현재 호스트 대화에 남아 있었다.

| 구간/크기 | 관측 |
| --- | ---: |
| 실제 CLI 추출 요청 반환 | 21,715바이트 |
| 같은 요청의 기존 루트 중복 형식 재구성 | 42,891바이트 |
| 호스트가 제출한 compact 문항 데이터 | 10,532바이트 |
| 최종 문항/생성 후보 | 30 / 30개 |
| 요청 CLI 호출 | 0.718초 |
| 추출 결과 제출 CLI 호출 | 0.334초 |
| 조합·서버 시작 CLI 호출 | 0.728초 |
| 요청 시작 → 정상 HTTP API 확인 | **81.232초** |

기존 반환 크기는 동일 저장 본문·요청 ID·조건으로 레거시 응답을 재구성한 값이다. 변환 후
직렬화 크기가 실제 CLI 출력 21,715바이트와 일치함을 assert했다. 이 크기 비교를 위해
추가 AI 생성을 수행하지 않았다. 이전 실제 제출 데이터는 9,457바이트였고 이번에는 개별
개념을 적는 등 문항/출력량도 달라졌다. 입력만 바꾼 통제 A/B가 아니다.

실제 호스트가 문항을 JSON 파일에 직접 작성해 CLI의 extract_batch와 assemble로 제출했다.
각 문항의 정답 이유·원문 인용을 작성/검토했고, 텍스트에 없는 그림 내용은 추측하지 않았다.
최종 서버의 실제 API 응답에서 30문항 상태와 시작 전 문항 비공개를 확인했다. 코드 실행은
하지 않았으며, 기본 객관식 사례다. 독립적인 교육 품질 평가나 브라우저 렌더링 측정은 아니다.

이전 69.886초 실행은 Python 내부 호출 중심의 하니스였고 이번에는 실제 CLI 프로세스와
기존 웹 실행기까지 사용했다. 호스트 대기에는 작성·검토·도구 왕복이 포함된다. 그러므로
**이번 변경에 신규 생성 속도 개선 수치를 부여하지 않는다.** 30~60초 목표도 달성했다고
하지 않는다. 원문 다운로드와 최초 의존성 설치는 이번 타이머에 포함하지 않았다.

[사건별 시각과 한계](../../../experiments/study-generation/results/handoff-live-java.json).
원문·문항·사용자 DB 복사본·시험 URL 토큰은 Git 바깥 테스트 폴더에만 보관한다.

## 검사

- 대학 기능 380개 중 **379개 통과**, 선택적 환경 검사 1개 건너뜀. 서버 **16개 통과**.
- 파이프라인 30개 검사는 위 전체 검사에 포함한다. 요청 보존·원본 비변경·두 부분 요청의
  재개/완료·기존 Python 반환·비추출 응답 보존을 검사했다.
- 실제 CLI의 자연어 요청 → v2 추출 응답 → compact JSON 파일 제출 → 후보 저장까지
  통합 검사했다. 기존 인용·권한·사용자 분리 검사는 전체 회귀에서 통과했다.
- 이 검사 결과는 `handoff-regression.*`에 따로 저장하고 기존 `regression.*`는 보존했다.

원시 검사: [요약](../../../experiments/study-generation/results/handoff-regression.json),

## 다음 판단

입력 전달 개선은 기능 검증을 통과했지만 속도 개선으로 보고하지 않는다. 이 코드의
추가 축약을 계속하기보다, 동일 출력 작업량을 고정한 호스트 비교를 먼저 해야 한다.
재생성의 캐시 부족분 보완은 반복 요청에만 별도로 측정하고, 신규 30문항이 계속 60초를
넘는다면 실제 지원되는 호스트 병렬 생성 실험을 검토한다. requests 두 개가 자동으로
독립 AI 호출이 되는 것은 아니다. 검증·해설·최종 문항 수를 줄여 목표를 맞추지 않는다.
