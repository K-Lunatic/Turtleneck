# 문제 생성 최적화 보고 메모

2026-11-06 · 실험 브랜치 전용 · 푸시하지 않음

목표는 Codex에서 약 3~4분 걸리던 30문항 생성을 수십 초로 줄이는 것이다.
자바2 실자료로 **30문항 저장 69.6초, 웹 API 준비 69.9초**를 관측했다.
**30~60초 목표에는 아직 못 미친다.** TLS 변경 감지 지문 가속과 구분한다.

- 분석 단위를 8,000→16,000자로 늘려 긴 자료의 분석 왕복을 줄였다.
- 여유 후보를 약 1.5→1.2배로 줄이고, 한 부분에서도 30문항을 확보할 수 있게 상한을 보완했다.
- 검토할 후보를 조합 응답에 동봉해 30문항의 별도 후보 조회 6회를 없앴다. 의미·정답 검토는 유지한다.
- 기존 분석 캐시, 인용·권한 검사를 유지하고, 요청부터 조합까지/호스트 전달 대기를 기록한다.
- 공통 문항 필드·선택지 번호·SOURCE 번호를 쓰는 간결한 제출 형식을 추가했다. 서버가 전체
  형식으로 복원한 뒤 같은 검증을 적용한다. 동등 30문항 JSON은 15,922→9,457바이트였다.

| 30문항 모의 실험, 각 30회 | 자료 1개 | 자료 4개 |
| --- | ---: | ---: |
| 분석 왕복 | 6→3회 | 8→4회 |
| 전체 도구 호출 | 14→5회 | 16→6회 |
| 생성 후보 | 55→36개 | 48→40개 |
| 로컬 처리 중앙값 | 236.889→153.241ms | 281.679→214.993ms |

위 표는 모의 응답의 로컬 실험이며 실제 AI 추론 시간과 구분한다.

실자료는 Java프로그래밍2 **제네릭과 컬렉션A.pdf**, 24쪽이다. 현재 호스트가 직접 작성한
첫 실행은 후보 36개에서 30개를 저장하는 데 103.8초, 간결한 실행은 필요한 후보 30개를
저장하는 데 69.6초였다. 같은 대화에서 자료를 이미 읽었고 질문·후보 수가 달라 엄밀한 A/B
개선율은 아니다. 객관식·짧은 해설의 사례로, 장문·코딩 문제까지 같은 속도를 보장하지 않는다.

기존 코드는 이 PDF에서 후보 예산이 20개에 막혀 같은 30문항 제출을 거부했다. 기존의
동일 자료 30문항 완료 시간이 없어, 사용자 경험인 3~4분 대비 단축률은 계산하지 않는다.
TLS 확인/파일 요청에는 별도로 80.9초가 걸렸다. 생성 타이머에는 포함하지 않는다.

검사 393개 통과·환경 의존 검사 1개 건너뜀. PDF 이미지 라이브러리가 없으면 텍스트까지
실패하던 경로도 수정했다. 웹 API 정상 응답과 시작 전 정답 비공개를 확인했다.

변경은 `.publish-tls`의 실험 체크아웃에만 적용된다. 원래 실행 경로나 설치된 플러그인은 자동 변경하지 않았다.

남은 목표: 새 자료·동일 유형으로 반복 측정하고 30~60초 달성, 실제 브라우저 렌더링과
문항 다양성·교육 품질 확인. 현재 수치만으로 실사용 전체의 확정적 개선율을 주장하지 않는다.
