# 문제 생성 속도 개선 기록

2026-11-06 · `experiment/rust-core-refactor` · 운영 브랜치/원격 미반영

## 목표와 현재 판정

사용자가 Codex에서 약 30문항 생성에 3~4분 걸렸다고 보고했다. 목표는 실제 웹 시험지를
수십 초 내 준비하는 것이다. 실제 자바2 자료에서 **30문항 저장 69.6초, 웹 API 준비 69.9초**를
관측했다. **30~60초 목표 달성으로 판정하지 않는다.** 동일 조건의 기존 모델 추론 시간은
없어 인과적인 전후 단축률도 주장하지 않는다. 기존 3~4분은 사용자의 경험값이다.

이 프로젝트는 호스트 Codex가 개념 분석과 문제 생성을 수행한다. Python은 자료를 전달하고
인용·형식·권한을 검증한 뒤 저장한다. 별도 모델 API 키나 SDK를 추가하거나 호스트의 모델을
임의로 바꾸지 않았다. Rust 파서 개선율을 문제 생성 속도 개선율로 사용하지 않는다.

## 변경과 이유

| 변경 | 이전 → 이후 | 이유/효과 |
| --- | --- | --- |
| 긴 원문 분할 | 8,000 → 16,000자, 묶음은 최대 두 부분 유지 | 전체 본문을 보존하면서 분석 왕복 감소 |
| 여유 후보 예산 | 최종 개수의 약 1.5 → 1.2배를 파일/부분에 배분 | 최종 30문항을 줄이지 않고 버리는 생성량 감소 |
| 부분 후보 상한 | 20 → 40개 | 한 부분뿐인 자료에서 30문항 요청이 구조적으로 20개에 막히는 문제 해소 |
| 조합 후보 검토 | 후보 5개씩 별도 조회 → 제안된 후보를 조합 응답에 동봉 | 기본 30문항의 후보 조회 6회 제거, 의미 검토 유지 |
| 검토 응답 상한 | 최대 30후보·후보 JSON 합계 60,000 UTF-8 바이트 | 큰 코드는 잘라내지 않고 남은 ID만 별도 조회 |
| 호스트 출력 | 필요한 유형 필드·간결한 해설을 지시, CLI JSON 공백 제거 | 불필요한 빈 필드와 장문 중간 출력 감소 유도 |
| 기존 분석 | 이전 8,000자 v3 분석도 재사용 | 설정/내용이 같은 자료를 새 분할 기준 때문에 재생성하지 않음 |
| 계측 | 요청 시작·완료 묶음·호스트 전달 대기 기록 | 다음 실제 생성의 지연을 확인할 수 있음 |
| 권한 | `extract_batch`도 기존 자료 권한 재확인 적용 | 생성 중 자료가 금지되면 묶음 저장도 중단 |
| 간결한 생성 형식 | 공통 기본값·선택지 번호·SOURCE 번호 인용 | AI가 반복 작성할 필드를 줄이고 저장 전 전체 형식으로 복원·동일 검증 |
| PDF 선택 의존성 | 이미지 라이브러리 ImportError가 텍스트 추출까지 실패시킴 → 텍스트 유지 | 실제 PDF 테스트에서 발견한 실패 수정 |

원문·출처 위치·이미지 참조·최종 문제 수·정답/인용 검증은 유지한다. 여유 후보 축소는 선택할
대안을 줄이는 변경이므로 실제 다양성과 정답 정확성은 실사용 검토가 필요하다. 부족한 경우
`shortageReason`을 유지하고 임의로 문제를 채우지 않는다. 200문항 전체 생성의 성능은 별도다.

## 30문항 로컬 전후 실험

동일한 합계 88,000자 텍스트를 자료 1개 또는 4개에 분배하고, 격리된 SQLite·파일·캐시에서
각각 30회 실행했다. 호스트 결과는 동일한 형태의 결정적 모의 응답이다. 실제 LLM 요청·의미
정확성·추론 시간은 측정하지 않았다. 모든 본문과 위치를 보존하고 최종 30개를 조합하는지
assert로 확인했다. 설치·자료 fixture 준비·모의 응답 작성·웹 서버 시작은 측정 밖이다.

| 측정값 | 자료 1개: 이전 → 이후 | 자료 4개: 이전 → 이후 |
| --- | ---: | ---: |
| 분석 묶음 왕복 | 6 → 3회 | 8 → 4회 |
| 독립 분석 부분 | 11 → 6개 | 12 → 8개 |
| 생성 후보 | 55 → 36개 | 48 → 40개 |
| 최종 문항 | 30 → 30개 | 30 → 30개 |
| 후보 검토용 별도 조회 | 6 → 0회 | 6 → 0회 |
| 전체 StudySession 도구 호출 | 14 → 5회 | 16 → 6회 |
| 로컬 호출 누적 중앙값 | 236.889 → 153.241 ms | 281.679 → 214.993 ms |
| 분석 재사용 후 준비 중앙값 | 19.909 → 19.335 ms | 33.516 → 33.125 ms |
| 재사용 시 AI 분석 요청 | 0 → 0회 | 0 → 0회 |

로컬 호출 누적은 Python `StudySession.call` 시간의 합이다. 프로세스 실행 비용, 도구 전송,
AI 대기, 실제 웹 시작까지 포함한 실사용 시간과 다르다. 전후 실험은 순차 실행으로 교대 쌍별
실험이 아니며 시간 수치는 해당 환경의 관측 중앙값이다. 원시 표본도 저장했다.

이 실험에서 총 도구 반환 JSON은 자료 1개 1,056,256→1,046,450바이트, 자료 4개
1,125,754→1,176,125바이트였다. 검토 내용을 동봉하므로 **통신량까지 항상 감소하는 것은
아니다.** 호환용 첫 부분과 requests의 원문 중복도 남는다. 공백 없이 직렬화한 반환 기준이며
모델 토큰 수나 실제 CLI 출력 전체를 측정한 값은 아니다.

## 실제 Java2 자료 테스트

사용자 요청에 따라 TLS에서 Java프로그래밍2의 **제네릭과 컬렉션A.pdf**를 확인/가져왔다.
PDF 24쪽·1,277,602바이트에서 텍스트 7,703자를 추출했다. SHA-256과 사건별 시각은
[live-java.json](../../../experiments/study-generation/results/live-java.json)에 있다. 원문·문항·사용자
DB 복사본·서버 토큰은 Git 바깥 작업 폴더에만 보관한다. 기존 학습 기록은 수정하지 않았다.
요청한 TLS 갱신은 정상 사용자 DB의 학사 메타데이터를 갱신했고, 해당 파일 요청은 1회였다.

| 실제 호스트 실행 | 관측 | 한계 |
| --- | ---: | --- |
| TLS 확인/파일 요청 | 80.907초, 291요청 | 기존 ensure가 전체 메타데이터도 확인함. 생성 타이머에서 분리 |
| 첫 실자료 실행 | 후보 36개 → 최종 30개, 저장 103.803초 | 현재 호스트에서 작성·검토한 단일 실행 |
| 간결한 형식 실행 | 후보 30개 → 최종 30개, 저장 69.612초 | 필요한 30개만 제공하고 여유 후보 부족 사유 명시 |
| 간결한 실행의 실제 HTTP API 준비 | 요청 시작부터 69.886초 | 화면 렌더링 시간은 포함하지 않음 |
| 같은 저장 분석의 로컬 재사용 | 준비 19.853ms + 조합 7.649ms | AI 재검토·서버 시작 제외. 새 문제 생성 시간 아님 |

간결한 실행은 같은 자료를 이미 읽은 현재 호스트 대화에서 수행했다. 모델 컨텍스트를
초기화하거나 모델/추론 설정을 통제한 반복 A/B가 아니다. 첫 실행과 후보 수·질문도 다르므로
103.8→69.6초를 순수 JSON 형식의 개선율로 계산하지 않는다. 자동 문제 생성 API를 새로
도입한 것이 아니라 **현재 호스트가 실제로 문항을 작성해 기존 이벤트에 제출**한 실행이다.
공통 필드는 로컬 스크립트로 조립했다. 이미지 내부는 추측하지 않았고 코드도 실행하지 않았다.
기본 객관식과 짧은 해설의 사례이며, 손코딩·장문 서술형이나 전체 개념 분석의 품질 검증은 아니다.

같은 30문항 데이터의 compact 제출 JSON은 **9,457바이트**, 전체 필드를 복원한 동등 JSON은
**15,922바이트**로 약 40.6% 작았다. 이는 바이트 비교이며 토큰 수나 지연 감소율이 아니다.
번호의 범위/타입과 실제 인용은 서버에서 검증하고 정규 저장 결과가 같은지 회귀 검사한다.

기존 `1a4f7e6` 코드에 같은 PDF와 30문항 요청을 적용하면 분석 부분은 하나인데 후보 예산이
20개에 막혀 30문항 제출을 거부했다. 따라서 이 파일에 대한 **기존 30문항 완료 시간은 없다.**
사용자가 경험한 3~4분과 이번 69.9초의 자료/조건이 달라 확정적인 개선율을 주장하지 않는다.

중간에 자동 승인 서비스의 사용량 제한으로 중단된 실행은 대기 5,804초가 섞여 성능 표본에서
제외했다. 재개 후 기능 검증은 통과했다. 원인과 제외 여부를 원시 결과에 보존한다.

측정용 Python에는 저장소의 선택 의존성 범위인 pypdf 6.21.4와 이미지 판독용 Pillow 13.0.0을
별도 폴더에 설치했다. 시스템 Python 설정이나 운영 플러그인은 바꾸지 않았다. 기존 환경은
PDF 판독기가 없었고, pypdf만 설치하면 Pillow 부재가 전체 텍스트 추출까지 실패시키는 경로가
있어 해당 예외를 수정했다. 그림 정보가 필요한 문제는 이미지가 실제 보이는 경우에만 만든다.

## 후속 실사용 검증 방법

1. 이 실험 체크아웃의 `skills/university-agent/scripts/run_agent.py`와 해당 SKILL을 사용하는
   Codex에서 이전과 같은 과목·자료·범위·난이도로 30문항을 생성한다. 원래 체크아웃이나 설치된
   플러그인을 실행하면 이 변경이 적용되지 않을 수 있다. 운영 소스/플러그인은 자동 교체하지 않았다.
2. `reusedFiles`이면 기존 분석을 쓰고 AI 분석을 반복하지 않는다. 신규 분석은 요청된 각 부분의
   개념과 문제를 한 번에 생성해 `extract_batch`로 제출한다. 원문 전체와 필수 검토를 생략하지 않는다.
3. `reviewQuestions`를 바로 검토하고 `reviewRemainingIds`에 있는 후보만 추가 조회한다. 부족하거나
   잘못된 후보는 보고/교체하며, 검토 후 `assemble`하고 실제 웹 링크까지 전달한다.
4. 최종 응답의 `generationMetrics`와 브라우저 링크 준비까지의 시간을 기록한다. 시험 시작 직전
   동일 유형·30문항·근거·정답·중복을 확인한다. 같은 조건으로 여러 번 비교하되 캐시 재사용 여부와
   Codex 모델/추론 설정을 분리한다. 재분석을 원할 때만 `rebuildAnalysis: true`를 명시한다.

`requestToAssemblySeconds`: pipeline 시작부터 조합 반환 직전까지. 최초 자료 선택/동기화와 웹
서버 시작은 포함하지 않는다. `hostHandoffSeconds`: 분석 묶음 공개부터 유효 결과 저장까지의
누적 벽시계 시간. 호스트 추론뿐 아니라 도구 왕복·재시도·중단 시간을 포함한다. 완료 묶음 수는
`completedBatches`에 남고 새로 생성한 시험의 상태에도 저장된다. 기존 시험에는 없을 수 있다.

로컬 처리 절감은 수십 ms이므로 이것만으로 180~240초가 30~60초가 됐다고 주장할 수 없다.
분석 왕복·생성 후보 감소의 실제 AI 효과를 확인한 뒤, 여전히 느리면 호스트 출력량/추론 대기와
문항 유형(특히 긴 코드·서술형)을 구분해 다음 변경을 결정한다.

## 재현과 증거

```powershell
# .publish-tls 루트에서. 모두 격리 fixture이며 실제 학교/사용자 DB를 수정하지 않는다.
$env:PYTHONUTF8='1'
python experiments/study-generation/benchmark.py --output experiments/study-generation/results/after.json
python experiments/study-generation/verify.py
```

별도 체크아웃에 benchmark.py만 복사해 실행한다. 현재 코드에서 before 파일을 덮어쓰면
원래 baseline이 아니므로 기존 파일을 보존한다.

회귀: 대학 기능 378개 중 377개 통과·1개 건너뜀, 서버 16개 통과. 추가 파이프라인 28개와
PDF/자료 16개 검사는 이 전체 검사에 포함한다. 최종 스키마 변경 후 해당 28개도 재확인했다.
실제 브라우저 렌더링·다른 OS·여러 모델의 반복 추론 속도·교육 품질의 독립 평가는 미검증이다.
