## 서버 트래픽 비교 상태

### 일반 크롤러 기준선과의 비교

버전 간 비교만으로는 “최신 터틀넥이 예전 터틀넥보다 낫다”만 알 수 있으므로, 별도의
재현 가능한 일반 크롤러 기준선도 추가했다. 기준선은 특정 외부 제품을 지칭하지 않는다.
로그인 이후 매 실행마다 수강목록 → 모든 과목 → 모든 활동 → 공지 본문을 깊이 우선으로
다시 읽고, 로컬 캐시·변경 감지·실행 결과 재사용을 하지 않는 단순 크롤러다. 파일 본문과
동영상은 받지 않고 동일한 학사 메타데이터 범위만 비교한다.

2026-11-16 (Asia/Seoul), macOS arm64, Python 3.11.6, 8과목 fixture를 3회 반복한 결과다.
인증은 이미 된 fixture 세션으로 고정했고, 실제 TLS 서버 접속은 포함하지 않았다.

| 같은 범위·8과목 | 요청 수 | 응답 본문 | 의미 |
| --- | ---: | ---: | --- |
| 일반 무캐시 크롤러, 매 실행 | 81 | 12,064B | 매번 전체 순회 |
| 터틀넥 cold | 97 | 12,704B | 첫 수집. 공지 상태 POST 16회 포함 |
| 터틀넥 warm | 9 | 5,312B | 변경 없는 반복 확인 |

따라서 변경 없는 반복 확인에서 터틀넥은 이 기준선보다 요청 수 **88.89%**, 응답 본문량
**55.96%** 적었다. 반대로 첫 수집은 공지 상태 확인 방식이 달라 일반 기준선보다 요청
16회가 많았으므로, 터틀넥이 모든 상황에서 일반 크롤러보다 적다고 주장하지 않는다.
원시 비교 실행은 `experiments/benchmarks/compare_crawler_baseline.py`로 재현할 수 있다.

### 2026-11-18 최신 재실행

현재 기능 커밋 `d13a3fd` 이후 최신 문서·실측 커밋(`b45657e`)에서 같은
8과목 fixture를 **10회** 재실행했다. 실제 TLS 접속·로그인·파일 다운로드는 포함하지 않았다.

| 같은 범위·8과목 | 중앙 요청 수 | 중앙 응답 본문 | 해석 |
| --- | ---: | ---: | --- |
| 일반 무캐시 크롤러 | 81 | 12,064B | 매 실행 전체 순회 |
| 터틀넥 cold | 97 | 12,704B | 첫 수집·공지 상태 확인 포함 |
| 터틀넥 warm | 9 | 5,312B | 변경 없는 반복 확인 |

warm 반복 확인은 무캐시 기준선보다 요청 수 **88.89%**, 응답 본문량 **55.96%** 적었다.
반대로 cold 수집은 기준선보다 요청 수와 본문량이 많으므로, 이 재실행도 “모든 상황에서
일반 브라우저보다 적은 트래픽”의 증거가 아니다. 서버 CPU·메모리·DB 사용량은 이 측정에
포함되지 않는다.

현재 결과에는 터틀넥의 요청 수와 요청·응답 본문량 계측값은 있지만, 실제 학생이 브라우저로 같은
작업을 수행한 기준값은 아직 없다. 브라우저 HAR를 시나리오별로 받아 `traffic_profile.py`로 개인정보
없는 요약을 만든 뒤에야 직접 비교할 수 있다.

### 2026-11-18 실서버 소량 재측정

저장된 인증과 기존 로컬 DB를 사용해 건국대학교 TLS에 **메타데이터만** 요청했다. 수강 과목은
8개였고, 로컬 복사본에서 1개 과목만 변경된 것으로 표시해 두 실행을 순차 비교했다. 파일 원본과
동영상은 받지 않았으며, 인증·사전 수강목록 준비는 비교 구간에서 제외했다.

| 같은 계정·8과목·1과목 갱신 | 이전 로직 | 현재 로직 | 감소 |
| --- | ---: | ---: | ---: |
| HTTP 요청 | 342회 | 12회 | **96.49%** |
| 응답 본문 | 1,357,840B | 138,085B | **89.83%** |
| 측정 시간 | 113.773초 | 4.876초 | **95.71%** |

두 실행 모두 선택 과목과 나머지 과목의 저장 결과가 일치했고, 원본 로컬 DB 해시도 변하지 않았다.
실측 결과는 `tls-optimization-results/live.json`에 집계값만 저장했다. 이 결과는 한 계정의 단회
실서버 측정이며, 학교 서버 CPU·DB 사용률이나 일반 학생 브라우저와의 비교를 증명하지 않는다.

| 비교 대상 | 현재 상태 |
| --- | --- |
| `academic_sync` | 스킬 계측 있음 · 사용자 HAR 대기 |
| `open_one_course` | 스킬 계측 범위에 추가 측정 필요 · 사용자 HAR 대기 |
| `download_one_file` | 파일 요청 계측 가능 · 사용자 HAR 대기 |
| `watch_one_lecture` | 미디어 계측 fixture 있음 · 실제 시청 HAR 대기 |

터틀넥이 서버 부담을 줄이기 위해 적용한 정책은 중복 실행 통합, 변경된 과목만 상세 조회, 공지·자료·
상태별 재사용 기한 분리, 요청 간격과 재시도 제한, 이미 받은 로컬 자료 재사용이다. 이 정책들은
“사람보다 반드시 적다”는 증명이 아니라, 같은 작업을 반복해서 서버에 다시 묻지 않도록 한 설계 근거다.
특히 학생이 같은 강의를 다시 보거나 같은 파일을 반복해서 열 때는 로컬 캐시가 재사용되므로, 사람의
브라우저가 매번 서버에서 다시 받는 범위보다 작아질 수 있다. 이 주장은 실제 HAR 비교로 확인하기
전까지는 가능성으로만 표시한다.

비교 결과의 `bodyBytesLowerBound`는 요청·응답 본문량의 하한이다. 브라우저와 스킬의 인증 방식,
캐시 상태, 압축, 서버 응답 변화가 다르면 같은 학생 행동을 기록해도 결과가 달라지므로, 로그인과
초기 준비를 제외한 동일 시나리오·동일 캐시 조건으로 측정한다. 학교 전체 회선의 1Gbps 같은 상한을
학생별 허용량으로 환산하지 않으며, 서버 CPU·메모리·DB 사용률은 별도 서버 계측 없이는 판정하지 않는다.
