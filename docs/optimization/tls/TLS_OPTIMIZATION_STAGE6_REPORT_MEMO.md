# TLS 최적화 추가 보고 메모 — 6단계부터

작성일: 2026-11-06 · 현재 범위: **6~8단계 완료** · 6단계 푸시 완료, **7·8단계 커밋·푸시하지 않음**

아래 첫 표는 기존 6단계 결과이며, 뒤에 7·8단계의 변경·효과를 추가했다. 비교 조건이 다르므로 감소율을 합산하지 않는다.

**변경:** 파일 1개를 요청할 때 같은 과목의 모든 자료 상세를 확인하던 방식에서, 목록이 그대로이고 자료 확인 기한이 유효하면 **지정 자료만 상세 확인**하도록 개선했다.

**이유:** 과목에 자료가 쌓일수록 파일 하나를 받기 위해 관계없는 자료의 상세 페이지·뷰어·문서 상태까지 반복 조회하는 비용이 커졌기 때문이다.

**동작:** 목록 변경·기한 만료·강제 확인·과목을 알 수 없는 자료 ID는 전체 확인을 유지한다. 공지의 다운로드 제한과 지정 자료 권한은 다시 확인하며 미조회 자료 기록은 보존한다. 일부 자료만 확인한 경우 과목 전체의 성공 시각을 최신으로 변경하지 않는다.

| 비교 | 변경 전 | 변경 후 | 효과 |
| --- | ---: | ---: | --- |
| 실제 TLS: 자료 36개 과목에서 1개 상세 확인 | 72회 | 2회 | **97.22% 감소** |
| 같은 상세 조회 구간의 응답 본문 | 20,559 B | 622 B | **96.97% 감소** |
| 같은 상세 조회 구간의 시간 | 19.469초 | 0.531초 | **97.27% 감소** |
| 모의 전체 명령: 20개 중 파일 1개 요청 | 53회 | 15회 | **71.70% 감소** |
| 모의 전체 명령: 20개 중 파일 3개 요청 | 55회 | 21회 | **61.82% 감소** |
| 모의 전체 명령: 100개 중 파일 1개 요청 | 213회 | 15회 | **92.96% 감소** |
| 모의 전체 명령: 20개 전부 요청 | 72회 | 72회 | 동일 |
| 모의 전체 명령: 강제 확인 또는 24시간 경과 | 134회 | 134회 | 동일 |

실제 TLS 수치는 **자료 상세 조회 구간만** 비교한 단회 실측이다. 로그인·목록·공지 읽기는 제외했고 원본 파일 본문은 받지 않았다. 전체 동기화의 97.22% 절감으로 해석하지 않는다. 실제 지정 자료의 확인 결과 일치와 원본 DB 보존을 확인했다.

모의 비교 8개 조건은 파일 수신까지 포함한 명령 전체를 측정했으며, 전후 저장 결과와 파일 SHA-256이 모두 일치했다. 자료가 많고 요청한 파일이 적을수록 효과가 크다. 추가 회귀 검사에서 권한·기존 기록·만료·오류·삭제·동시 호출 재사용을 검증했다.

6단계 당시 검사 결과: **369개 중 367개 통과·실패 0개·환경 의존 검사 2개 건너뜀**. 대학 기능 351개, 서버 16개 통과다.

학교 서버 내부 CPU·DB 사용량은 미측정이며, 네트워크 실측의 전체 동기화 시간과 실제 파일 다운로드 속도는 비교하지 않았다. 기존 0~5단계 메모와 별도로 이 문서부터 추가 결과를 누적한다.

상세 동작·조건·원시 수치·재현 명령: [6단계 이후 상세 기록](TLS_OPTIMIZATION_STAGE6_RESULTS.md)

## 7·8단계 추가 보고

| 단계 | 바꾼 내용 | 이전과의 차이·이유 |
| --- | --- | --- |
| 7. 공지 목록·본문 분리 | 목록 행이 같고 6시간 이내인 본문을 재사용 | 과제 등 다른 활동이 바뀔 때 기존 공지까지 다시 읽는 요청 감소 |
| 8. 변경된 값만 DB 반영 | 같은 값의 UPDATE를 생략하고, 동기화 상태도 바뀐 키만 저장 | 부분 수집 때 전체 기록을 반복 수정하던 로컬 쓰기 감소 |

7단계는 새 글·목록 변경이 보이면 본문을 읽는다. 조회수·행 번호는 변화에서 제외하되, 제목·작성일 등은 비교한다. **본문만 수정돼 목록이 같아도 기존 6시간 기한 이후 다음 확인 때 전체 본문을 다시 읽는다.** 재사용으로 이 기한을 연장하지 않는다. 강제·파일 권한 확인·알 수 없는 목록 형식·캐시 없음은 전체 읽기를 유지한다.

| 실제 비교 조건 | 변경 전 | 변경 후 | 효과 |
| --- | ---: | ---: | --- |
| TLS 공지 7개, 기한 내 일반 재조회 요청 | 8회 | 1회 | **87.50% 감소** |
| 같은 공지 구간의 읽은 응답 본문 | 85,620 B | 10,402 B | **87.85% 감소** |
| 같은 공지 구간의 시간 | 3.109초 | 0.297초 | **90.45% 감소** |
| 실제 사용자 DB 복사본, 동일 내용 재저장 | 180행 변경 | 1행 변경 | **99.44% 감소** |

실제 공지 비교는 로그인·과목 목록·캐시 준비를 제외한 **공지 재조회 구간의 단회 측정**이다. 전체 동기화 감소율이 아니다. DB 비교는 사용자 원본을 읽기 전용 백업한 임시 DB에서 했고, 사용자 시각 1행은 계속 갱신한다. 공지 내용과 저장된 학업 정보 일치, 원본 DB 보존을 확인했다.

| 동일 입력 모의 비교 | 변경 전 → 후 |
| --- | ---: |
| 과목 목록 변경·기존 공지 20개 동일: 전체 HTTP 요청 | **38→18회 (52.63% 감소)** |
| 같은 조건의 실제 DB 변경 행 | **664→12행 (98.19% 감소)** |
| 과목 목록 변경·기존 공지 100개 동일: 전체 HTTP 요청 | **118→18회 (84.75% 감소)** |
| 1,000개씩 있는 내용이 같은 데이터 재저장 | **7,002→1행** |
| 동기화 상태 100키 중 1개 변경 | **200→1행** |
| 6시간 만료·강제 확인·파일 권한 확인 | HTTP 요청 수 동일 |

7단계만 적용하면 새 캐시를 저장하면서 DB 쓰기가 늘 수 있어 8단계와 함께 비교했다. 12개 모의 HTTP 조건 모두 학업 정보가 일치했고, NULL 전환·상태·권한·삭제·계정 분리도 검사했다. 원시 파일: [최종 실측](../../../tls-optimization-stage78-results/live.json), [동일 입력 비교](../../../tls-optimization-stage78-results/offline.json), [회귀 검사](../../../tls-optimization-stage78-results/tests.json).

7·8단계 최종 회귀 검사: **384개 중 382개 통과·실패 0개·환경 의존 검사 2개 건너뜀**. 신규 검사 15개를 포함하며 대학 기능 366개와 서버 16개가 통과했다.

DB 변경 행 수는 **물리 디스크 쓰기나 학교 서버 DB 부하가 아니다.** 같은 값인지 비교하는 SQL은 남아 있다. 서버 CPU·메모리·DB 사용률은 미측정이고, 기존 호출 주기 밖의 새 공지를 즉시 감지하는 기능은 추가하지 않았다. **7·8단계는 아직 커밋·푸시하지 않았다.**
