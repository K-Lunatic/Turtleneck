# TLS 수집 부하 최적화 메모

작성일: 2026-11-05

진행 상태: **0~5단계 구현 및 변경 전후 측정 완료.** 실제 TLS와 고정 HTTP 응답 비교는 [통합 기록](TLS_OPTIMIZATION_RESULTS.md), 간단한 보고는 [보고용 메모](TLS_OPTIMIZATION_REPORT_MEMO.md)에 정리했다. 푸시는 하지 않았다.

## 목표와 범위

학교 TLS에 보내는 요청 횟수와 전송량을 줄이되, 과제 마감·제출 상태·강의 시청 상태의 정확성을 유지한다. UI·UX와 문제 생성은 이번 범위에서 제외한다. 연결 담당자가 수정하는 파일과 겹칠 수 있으므로 수집 로직 변경 범위를 먼저 공유한다.

아래는 최초 실행 계획과 적용 결과다. 0~2단계와 3~5단계의 비교 기준을 나눠 측정했으며 서로 다른 조건의 감소율을 합산하지 않는다.

## 최종 적용 정책

| 순서 | 적용 결과 | 확인한 효과 |
| --- | --- | --- |
| 0 → 1 → 2 | HTTP 계측 → 사전 페이지 재사용 → 변경 과목만 상세 확인 | 기존 실제 조건에서 요청 294→18회 |
| 3 | 같은 DB의 동기화 공통 잠금과 성공 결과 재사용 | 최근 상태 실제 재조회 57→0회, 동시 2프로세스 모의 요청 [3, 0]회 |
| 4 | 목록 5분·과제/시청 15분·공지 6시간·자료 24시간으로 성공 확인 시각 분리 | 같은 최신 상태를 얻는 모의 요청 50→41회, 공지 갱신 97→65회 |
| 5 | 리디렉션 포함 0.25초 간격, 제한 재시도, 서버 대기 시간 보존 | 실제 강제 갱신 최대 1초 요청 7→4회; 시간은 14.719→18.703초로 증가 |

주기는 호출할 때 검사하는 재사용 기한이며 새 예약 주기가 아니다. 목록이 같아도 만료된 상태를 확인한다. 즉시 최신 상태가 필요하면 `--academic-only --force`, 전체 확인은 `--full`을 사용한다. 일일 보고는 이미 강제 상태 확인을 사용한다. 서버 대기 제한은 강제 옵션으로 우회하지 않는다. 지정 파일 요청은 공지·자료 제한을 다시 확인한다.

게이트웨이 전체 성공 결과는 60초 재사용하며 같은 DB의 잠금을 공유한다. 다른 DB·기기까지 묶는 전역 제한은 아니다. 구현 상세와 측정 조건·본문 바이트·검사 결과는 통합 기록을 기준으로 한다.

## 현재 구조

- 학교 정보와 파일을 로컬에 저장하며, 자료 추출 결과에도 캐시가 있다.
- 일반적인 스마트 동기화는 성공 결과의 재사용 기한을 먼저 확인한다. 목록 확인이 필요하면 수강 과목·활동 목록을 읽고 변경되거나 범위별 기한이 지난 상세만 확인한다.
- 자동 확인은 기본 6시간 간격과 아침 7시 일정이 있으며, 예약 실행에는 최근 5시간 이내 중복 확인 방지와 최대 15분의 실행 시점 분산이 있다. 실제 실행 여부는 스케줄 설치 상태에 따른다.
- 자동 확인의 일반 경로는 파일 본문을 받지 않는다. 일일 보고 경로는 과제·강의 상태를 별도로 새로 확인한다.
- 따라서 첫 다운로드 이후에도 페이지 조회 요청은 남는다. 이용자 수·과목 수·확인 빈도가 늘면 이 요청이 누적된다.

## 실행 순서

### 0단계 — 요청량 측정과 정확성 기준 확보

**바꿀 내용**

- `providers/moodle_session.py`의 실제 HTTP 요청 경계에 측정을 추가한다.
- 동기화 1회당 요청 수, 응답 본문 바이트, 소요 시간, 응답 상태를 집계한다. 페이지·파일 요청을 구분하고 로그인 확인 요청도 포함한다.
- 변경 없음, 한 과목 변경, 제출·시청 상태만 변경, 새 파일 요청을 기준 시나리오로 남긴다.
- 로그에는 쿠키·비밀번호·응답 본문·개인 식별 쿼리를 남기지 않는다.

**이유**: 시간이 오래 걸리는 부분과 TLS 요청이 많은 부분은 다를 수 있다. 기준값이 있어야 실제 부하 절감을 확인할 수 있다.

**기대 효과**: 이후 작업의 우선순위와 절감 효과를 수치로 판단할 수 있다.

**완료 기준**: 같은 시나리오를 구현 전후 비교할 수 있고, 결과 데이터의 정확성도 함께 확인할 수 있다. 본문 바이트는 전체 네트워크 전송량과 구분해 기록한다.

### 1단계 — 사전 확인에서 받은 과목 페이지 재사용

**바꿀 내용**

- `providers/moodle_provider.py`의 `preflight()`가 병렬 작업에서 읽은 과목 페이지를 이후 수집에서도 재사용하도록 전달한다.
- 같은 동기화 안에서 동일한 과목 페이지를 다시 요청하는 경로를 제거한다.
- 우선 한 번의 동기화 안에서만 재사용하고, 실행 간 영구 페이지 캐시는 추가하지 않는다.

**이유**: 현재 병렬 사전 확인은 자식 provider에 페이지를 보관한다. 이후 본 수집의 provider가 이를 재사용하지 못하면 같은 페이지를 다시 읽게 된다.

**기대 효과**: 변경이 발견되어 상세 수집으로 넘어갈 때 중복 페이지 요청과 HTML 전송량이 줄어든다.

**완료 기준**: 병렬 사전 확인 뒤 상세 수집에서 동일 과목 페이지를 다시 요청하지 않으며, 기존 수집 결과가 유지된다.

### 2단계 — 변경된 과목만 상세 수집

**바꿀 내용**

- `scripts/sync_tls.py`의 변경 판정을 전체 변경 여부에서 변경된 과목 ID 집합으로 확장한다.
- `providers/moodle_provider.py`의 상세 수집에 대상 과목 범위를 전달한다.
- 새 과목은 수집하고, 대상 파일이 로컬에 없으면 해당 과목·자료를 필요한 범위에서 수집한다.
- 부분 수집 저장 시 대상 밖 과목 데이터는 보존한다. 대상 과목 안의 삭제된 활동과 실제 수강 목록에서 사라진 과목은 별도 기준으로 처리한다.
- 캐시 형식 변경 등 전체 갱신이 필요한 경우는 유지한다.

**이유**: 현재 과목별 지문 비교 결과는 전체 변경 여부로 합쳐지므로, 일부 과목 변경이 전체 상세 수집으로 이어질 수 있다.

**기대 효과**: 한 과목이 바뀌었을 때 다른 과목의 과제·강의·공지·자료 상세 요청을 줄인다. 과목 수가 많을수록 효과가 커질 가능성이 있다.

**완료 기준**: 한 과목 변경 시 다른 과목의 상세 요청이 발생하지 않고, 다른 과목의 저장 데이터도 지워지지 않는다. 과목·활동의 추가와 삭제를 정확히 처리한다.

### 3단계 — 수동·자동 동기화의 중복 실행 통합

**바꿀 내용**

- `scripts/academic_watch.py`의 예약 실행 보호와 `scripts/sync_tls.py` 등 직접 진입 경로를 점검해, 같은 계정·로컬 저장소의 수집이 겹치지 않게 한다.
- 진행 중인 동기화가 있으면 새 수집을 시작하지 않고 기존 작업 상태를 안내하거나 결과를 재사용한다.
- 최근 결과는 필요한 확인 범위가 충족되고 성공적으로 저장된 경우에만 재사용한다.
- 과제·시청 상태 확인, 목록 확인, 특정 파일 다운로드를 구분해 필요한 작업이 잘못 생략되지 않게 한다. 명시적 새로고침도 구분한다.

**이유**: 자동 확인의 잠금·최근 확인 방지만으로 모든 수동 호출 경로가 보호된다고 볼 수 없다.

**기대 효과**: 여러 창이나 연속 명령에서 같은 요청 묶음이 중복 발생하는 것을 줄인다.

**완료 기준**: 같은 저장소에서 동시에 두 번 호출해도 실제 수집은 중복되지 않으며, 실패 후 잠금 복구와 필요한 추가 수집이 정상 동작한다.

### 4단계 — 정보 종류별 확인 주기 분리

**바꿀 내용**

- 과제 제출·강의 시청 상태, 활동 목록, 공지·자료 상세의 마지막 성공 확인 시각을 구분한다.
- 제출·시청 상태는 활동 목록 지문과 별개로 정기 확인한다.
- 오래된 항목과 변화가 적은 상세 정보의 재확인 빈도를 측정 결과에 따라 낮춘다. 파일 본문은 요청 시 수집하는 기존 방식을 유지한다.
- 각 정보의 확인 시각을 유지하고, 확인 실패를 최신 정보나 정보 없음으로 처리하지 않는다.

**이유**: 모든 정보에 같은 확인 주기를 적용하면 불필요한 조회가 생긴다. 반대로 활동 목록이 그대로라는 이유로 상세 상태를 계속 생략하면 제출·출석·본문 수정 등을 놓칠 수 있다.

**기대 효과**: 정확성이 필요한 상태 확인을 유지하면서, 변화가 적은 정보의 반복 요청을 줄인다.

**완료 기준**: 활동 목록 변화 없이 제출·시청 상태나 기존 공지 내용만 바뀐 경우도 해당 기한 이후의 다음 동기화에서 반영된다. 호출 자체가 없으면 주기 내 반영을 보장하지 않는다.

### 5단계 — 순간 부하와 실패 후 재요청 제한

**바꿀 내용**

- `providers/moodle_session.py`의 요청 간격과 `providers/moodle_provider.py`의 동시 작업 수를 함께 점검한다. 기존 0.08초 간격을 리디렉션 포함 0.25초로 변경했고 병렬 작업 수는 유지했다.
- 측정된 요청량과 서버 응답을 바탕으로 동시 요청·초당 요청을 제한한다.
- 429 응답의 `Retry-After`를 존중하고, 재시도가 필요한 일시 오류에는 횟수 제한과 대기 증가를 적용한다. 즉시 반복 재실행도 방지한다.
- 기존 실행 시점 분산을 유지한다. 제한은 한 기기·프로세스 범위인지 명확히 하고 학교 전체 요청 상한으로 해석하지 않는다.

**이유**: 요청 수를 줄여도 짧은 순간에 몰리거나 실패 직후 반복하면 서버에 부담을 줄 수 있다.

**기대 효과**: 순간 요청 집중과 오류 상황의 재요청 폭증을 줄인다. 대신 수집 완료 시간은 늘어날 수 있다.

**완료 기준**: 병렬 작업에서도 의도한 요청 제한을 지키고, 429·일시 오류 때 즉시 반복하지 않는다. 권한·로그인 오류는 무의미하게 재시도하지 않는다.

## 우선 적용 범위

첫 작업은 **0 → 1 → 2단계**로 묶는다. 기준값을 확보하고 중복 페이지 요청을 제거한 뒤 변경 과목만 수집한다. 이 단계가 끝나면 요청 수·본문 바이트·결과 정확성을 비교한다.

이후 **3 → 4 → 5단계**로 진행한다. 여러 진입점의 중복을 막고, 최신성 요구에 맞춰 확인 주기를 나눈 다음, 남은 요청의 순간 집중과 오류 재시도를 조절한다.

## 보류할 항목과 주의점

- 조건부 요청은 파일 재검증에 이미 사용된다. HTML 페이지까지 확대하려면 TLS가 유효한 `ETag`·`Last-Modified`·304 응답을 제공하는지 먼저 확인한다. 304도 서버 요청 자체를 없애지는 않는다.
- 페이지 캐시를 늘리거나 확인 주기를 무작정 늘리는 방식은 상태 변경과 접근 제한 변경을 놓칠 수 있어 먼저 적용하지 않는다.
- 기존 자료 재사용에서도 접근·다운로드 제한 검증을 생략하지 않는다.
- 이용자 간 TLS 응답 공유 캐시는 계정별 권한과 개인정보가 섞일 수 있으므로 이번 범위에서 제외한다.
- 절감률은 측정 후 기록한다. 개인 환경의 개선 결과를 학교 전체 규모의 부하 보장으로 일반화하지 않는다.

최초 계획 이후 사용자 요청에 따라 0~5단계를 순서대로 적용했다. 변경·측정·검증 내역과 한계는 위 통합 기록을 기준으로 확인한다.
