# 터틀넥 문제·회귀 기록

이 문서는 기능 소개가 아니라, 실제 개발·테스트 중 발견한 문제를 재발 방지용으로 기록한다.
새 문제가 생기면 `증상 → 원인 → 해결 → 검증 → 남은 위험` 순서로 추가한다.

## 상태 표기

- **해결**: 코드와 회귀 검사를 확인했다.
- **부분 해결**: 일반 경로는 보완했지만 특정 학교·OS·실계정 검증이 남았다.
- **미측정**: 실패를 숨기지 않고 결과를 남겼지만 성공 수치를 만들지 못했다.

## 인증·세션·로그인

### 1. 진행 기록 저장이 `readonly database` 또는 `database is locked`로 실패

- **증상**: 과제명을 찾은 뒤 저장 단계에서 읽기 전용 DB 또는 SQLite 잠금 오류가 발생했다.
- **원인**: 읽기 전용 연결과 쓰기 연결이 같은 초기 트랜잭션을 공유했고, 저장 직전 커밋이 보장되지 않았다. 과제명에 `-` 같은 문자가 있으면 검색어 처리도 정확한 이름을 놓쳤다.
- **해결**: 정확한 과제명 우선 검색, 읽기·쓰기 연결 분리, 쓰기 전 명시적 커밋과 트랜잭션 보장을 적용했다.
- **검증**: 저장·불러오기·특수문자 과제명·SQLite 잠금 회귀 검사.
- **상태**: 해결.

### 2. 로그인 폼이 여러 번 뜨거나, 저장된 계정을 두고 다시 입력을 요구

- **증상**: 여러 채팅·명령을 실행하면 같은 계정의 로그인 폼이 반복되고, 브라우저 세션과 Keychain/Windows 보호 저장소 세션을 서로 다른 것으로 취급했다.
- **원인**: 프로세스 안의 세션 재사용만 있었고, 서로 다른 프로세스가 동시에 세션 만료를 발견하면 모두 로그인 절차를 시작했다. 저장된 빈 비밀번호를 실제 자격증명처럼 처리한 경로도 있었다.
- **해결**: 유효한 세션은 프로세스 메모리에서 재사용하고, 프로세스 간 프로필별 `.auth` 잠금으로 한 번만 인증한다. 대기한 실행은 잠금 해제 뒤 보호 저장 세션을 다시 확인한다. 빈 보호 저장소 값은 명시적 재연결로 종료한다.
- **검증**: 인증 회귀 18개, 전체 로컬 회귀 529개, macOS·Windows CI 24개 job.
- **상태**: 해결. 보호 저장소 자체가 비어 있거나 OS 권한이 거부되면 사용자의 한 번의 재연결은 필요하다.

### 3. 입력만 받았는데 로그인 성공으로 표시

- **증상**: 아이디·비밀번호를 입력하면 실제 TLS 로그인이 실패해도 등록 완료처럼 보일 위험이 있었다.
- **원인**: 폼 제출과 학교 로그인 검증이 분리되지 않았다.
- **해결**: 실제 학교 로그인, 세션 확인, 보호 저장소 저장까지 성공해야 성공 문구를 반환한다.
- **검증**: 잘못된 비밀번호·세션 저장 실패·성공 후 세션 복구 회귀.
- **상태**: 해결.

### 4. 웹 페이지를 열었다고 보고했지만 실제로는 열리지 않음

- **증상**: 로그인·시험 웹 화면을 열었다고 답했지만 브라우저에 페이지가 없거나 읽기 전용 상태였다.
- **원인**: `webbrowser.open()` 호출 결과를 실제 페이지 로드 확인으로 오인했다.
- **해결**: 접수 신호와 페이지 로드 신호를 분리하고 `opened` 상태를 명시한다. 열기 실패 시 URL만 안내한다.
- **검증**: 브라우저 열기 성공·실패, 보조 앱 우선·브라우저 fallback 회귀.
- **상태**: 해결.

## TLS·Moodle 수집·트래픽

### 5. 변경 없는 과목까지 상세 페이지와 공지를 모두 재조회

- **증상**: 한 과목만 바뀌어도 전체 과목의 과제·강의·공지·자료를 다시 읽었다.
- **원인**: 목록 재사용과 과목별 지문 비교가 없었고, 공지 목록과 본문 캐시 주기가 분리되지 않았다.
- **해결**: 과목 지문, 범위별 TTL, 공지 목록/본문 분리, 변경된 값만 DB 반영, 공통 잠금과 성공 결과 재사용을 적용했다.
- **검증**: 9과목 중 1과목 갱신 실측, 소량·대량 오프라인 벤치마크, 7·8단계 회귀.
- **상태**: 해결된 코드 경로. 학교 서버 CPU·DB 사용률은 측정하지 않았다.

### 6. 자료 두 개를 받는 데 28분 이상 소요

- **증상**: 파일 수는 적은데 자료 목록 갱신, 권한 재확인, 세션 재인증, 제한된 재시도가 겹쳐 다운로드가 매우 늦었다.
- **원인**: 새 자료를 로컬 색인에 먼저 반영해야 했고 파일별 접근·다운로드 허용 상태를 다시 확인했다. 서버 요청 간격과 재시도 대기도 적용됐다.
- **해결**: 목록·권한·원본 다운로드 단계를 분리하고, 이미 받은 파일은 검증자와 해시를 재사용한다. 선택 자료만 준비하며 실패 파일은 성공으로 저장하지 않는다.
- **검증**: 캐시·재검증·부분 실패·선택 자료 회귀와 소량/대량 fixture 벤치마크.
- **상태**: 부분 해결. 실 TLS에서 동일 파일 두 개의 개선 전후 평균은 아직 측정하지 않았다.

### 7. 다운로드 제한을 일반 오류로 처리하거나 금지 자료를 학습에 사용

- **증상**: 뷰어 주소와 실제 다운로드 금지를 구분하지 못하거나 제한 자료를 분석하려는 경로가 생길 수 있었다.
- **원인**: URL 표식, 과목 화면 안내 문구, HTTP 403, 문서 상태 응답을 하나의 상태로 다뤘다.
- **해결**: `PROHIBITED`·`NOT_DOWNLOADED`·`DOWNLOADED`를 분리하고 제한 근거를 저장한다. 금지 자료는 바이트 요청·학습 입력에서 제외한다.
- **검증**: URL 제한, 화면 문구, 403, 상태 API, 학습 제외 회귀.
- **상태**: 해결된 정책 경로. 학교별 제한 표시가 다른 경우 추가 adapter 검증이 필요하다.

### 8. 음원 변환 중 프로세스가 종료되면 HLS 재개 지점도 사라짐

- **증상**: 음성 추출이 영상 수신 뒤 변환 단계에서 중단되면 임시 폴더가 삭제되어 다음 실행이 처음부터 다시 받을 수 있었다.
- **원인**: 상위 음원 추출 함수가 `TemporaryDirectory` 안에서 원본 staging 파일을 만들었다. 하위 미디어 수집기의 `.partial` 체크포인트 수명보다 짧았다.
- **해결**: 강의·사용자·원본 지문별 로컬 staging 경로를 사용하고, 변환 실패 시 원본과 `.partial`을 남기며 성공 시 staging만 정리한다. 비밀값이나 학교 원본 주소는 기록하지 않는다.
- **검증**: 임시 연결 실패 후 체크포인트 보존·재시도·성공 후 staging 정리 회귀와 미디어 관련 70개 테스트.
- **상태**: 해결된 코드 경로. 장시간 실서버와 Windows 파일 잠금은 별도 실기기 검증이 남았다.

### 8. 강의 영상·음성 다운로드 중단 후 처음부터 재시작

- **증상**: 큰 MP4 또는 HLS 조각 다운로드가 끊기면 이미 받은 데이터도 버려졌다.
- **원인**: 목적지 옆 부분 파일과 완료 조각 상태가 없었고 직접 MP4의 Range 재개가 호출되지 않았다.
- **해결**: `.partial`과 manifest를 사용하고 완료 조각을 건너뛴다. MP4는 서버가 `206 Content-Range`를 정확히 제공할 때만 이어받는다.
- **검증**: HLS 중단·재개, 직접 MP4 Range 재개, 손상/HTML 응답, 파일 크기 제한 회귀.
- **상태**: 코드 해결. 실제 장시간 강의와 Windows 파일 잠금은 실기기 미검증.

### 9. 실서버 최적화 벤치마크가 타임아웃 또는 응답 불일치

- **증상**: 저장 세션으로 재시도해도 실서버 응답이 늦거나 두 순차 결과가 일치하지 않아 비교 수치를 만들지 못했다.
- **원인**: 학교 서버 응답·동적 상태·네트워크가 단회 측정 조건을 바꿨다.
- **해결**: 성공한 `live.json`을 보존하고 실패 실행은 `live-attempt.json`에만 기록한다. 실패를 성능 향상으로 환산하지 않는다.
- **검증**: 타임아웃과 불일치 실행 모두 `NOT_MEASURED`로 기록되는지 확인.
- **상태**: 미측정. 실서버 부하·실트래픽 감소율은 아직 95점으로 평가할 수 없다.

### 9-1. 실서버 부분 갱신 비교에서 미변경 자료 보존 검사가 실패

- **증상**: 2026-11-17 저장 연결 재사용 실행에서 선택한 한 과목의 결과는 일치했지만, 미선택 과목의 `resources` 보존 검사만 실패했다. 요청은 303회에서 12회로 줄었지만 이 상태에서는 성능 수치를 채택할 수 없다.
- **원인**: 현재 수강 과목이 9개에서 8개로 바뀐 상태에서, 비교기가 수강 취소된 과목의 과거 자료까지 “미선택 과목 자료”로 포함했다. 제품의 부분 보존 경로가 아니라 벤치마크 비교 범위 오류였다.
- **해결**: 보존 비교를 현재 수강 과목 집합으로 제한하고, 실패 시 성공 수치를 저장하지 않는 안전장치는 유지했다. 원본 자료·과목명·URL·인증값은 기록하지 않는다.
- **검증**: 2026-11-20 실서버 재실행에서 선택 과목과 현재 수강 중인 다른 과목의 자료가 모두 일치했다. 요청은 **303→12회(96.04% 감소)**, 응답 본문은 **1,047,937→120,683B(88.48% 감소)**, 실행 시간은 **88.11→3.91초(95.56% 감소)**였다. 원본 DB 해시도 동일했다.
- **상태**: 해결. 이 수치는 8과목·단일 계정·메타데이터 전용·순차 단회 비교이며 학교 서버 CPU/DB 사용률을 의미하지 않는다.

## 백업·자율강좌·문제은행

### 10. 자율강좌 백업 업로드가 큰 파일을 메모리에 올림

- **증상**: `.mbz` 업로드와 복구 준비가 파일 크기에 따라 메모리를 크게 사용했다.
- **원인**: multipart 본문을 `read_bytes()`와 `join()`으로 만들던 경로가 있었다.
- **해결**: Moodle 업로드는 파일을 읽는 스트리밍 body로 전송한다. 복구 양식·CSRF·소유권 확인은 유지하고 실제 쓰기 요청은 별도 승인 뒤에만 실행한다.
- **검증**: 대용량 가상 백업 스트림, 업로드 양식, 보호 필드 회귀.
- **상태**: 해결.

### 10-1. 백업 재구성 경로에 남아 있던 바이너리 전체 메모리 적재

- **증상**: 자율강좌 백업을 새 구조로 재구성할 때는 업로드 경로와 별개로 원본 `.mbz`의 모든 파일을 메모리에 읽었다.
- **원인**: `rebuild_moodle_backup.py`가 XML과 이미지·첨부를 같은 딕셔너리에 저장했다.
- **해결**: 구조 변경에 필요한 XML만 메모리에 읽고, 유지되는 비XML 파일은 원본 tar에서 새 tar로 스트리밍 복사한다.
- **검증**: 바이너리 자산 보존 회귀와 기존 백업 재구성 검사 통과. 2026-11-17 macOS 개발 환경에서 32MiB 바이너리 fixture를 포함해 재구성했을 때 추가 RSS는 약 224KiB였고, 출력 백업 검증도 통과했다.
- **상태**: 해결된 코드 경로. 실제 학교 백업 전체 크기의 최대 RSS와 Windows 실기기 측정은 남았다.

### 10-2. 재구성 백업의 토픽 수 메타데이터가 개요 토픽을 누락

- **증상**: 개요 토픽을 포함해 생성한 백업의 실제 section 목록과 `course.xml`의 `numsections`가 달라질 수 있었다.
- **원인**: 과목 메타데이터를 과목 토픽 수만으로 설정하고, 선택적으로 추가되는 개요 토픽을 세지 않았다.
- **해결**: 실제 생성 목록인 `topic_names`의 길이를 `numsections`에 사용한다.
- **검증**: 개요 1개와 과목 토픽 2개의 백업에서 section 목록과 `numsections=3`을 함께 확인했다.
- **상태**: 해결.

### 11. 문제은행 백업 생성 시 이미지·첨부 파일이 누락되거나 메모리 사용 증가

- **증상**: 백업 템플릿의 자료가 새 퀴즈 활동에 복사되지 않거나 큰 백업에서 메모리 부담이 커질 수 있었다.
- **원인**: `.mbz`의 모든 member를 딕셔너리에 넣어 바이너리까지 한 번에 읽었다.
- **해결**: XML 제어 파일만 메모리에 두고 비XML 자료·이미지는 입력 tar에서 출력 tar로 스트리밍 복사한다.
- **검증**: 기존 활동 바이너리 보존, 문제은행 백업 재검증, 관련 회귀와 CI.
- **상태**: 해결된 코드 경로. 실제 학교 백업 업로드·복구는 쓰기 검증 전 단계다.

### 12. 교수 권한을 `운영자`로만 판별

- **증상**: 실제로 교수 권한과 수정 링크가 있는데도 자율강좌 편집을 거부했다.
- **원인**: 역할 문자열 하나만 권한 근거로 사용했다.
- **해결**: 교수·교수자·교사·teacher·manager 계열 역할과 실제 수정 링크를 함께 확인한다.
- **검증**: 교수 역할 fixture, 자료 추가 양식, `files`·`sesskey` 필드 회귀.
- **상태**: 해결된 판별 경로. 실제 XML 등록·수정 POST는 별도 승인 전 미실행.

## 학습·시험·파일 처리

### 13. 시험 문제가 대화에 노출되고 웹 시험지가 열리지 않음

- **증상**: 문제 생성 결과가 채팅에 직접 출력되거나 브라우저가 열리지 않아도 준비 완료처럼 보였다.
- **원인**: 생성·저장·웹 전달 상태가 하나의 응답으로 묶여 있었다.
- **해결**: 파일별 후보를 저장하고 완성된 문항부터 웹 시험지에 전달하며 `delivery=web`과 `opened` 결과를 강제한다.
- **검증**: 시험 웹 열기 성공/실패, 문제은행 캐시 재사용, 부분 생성 상태 회귀.
- **상태**: 해결된 계약 경로. 저성능 AI·대량 문제 생성의 실시간 체감 시간은 환경별 차이가 남는다.

### 14. PDF/PPT 이미지가 tpack에 포함되지 않거나 화면에 이름만 표시

- **증상**: 자료 본문은 읽히지만 이미지 참조가 누락되어 학습팩·시험 화면에서 파일명만 보였다.
- **원인**: 이미지 추출 결과와 tpack manifest/자산 경로 연결이 분리되어 있었다.
- **해결**: 이미지 참조와 자산을 학습팩에 함께 보존하고, 실제 이미지가 있을 때만 렌더링한다. 없으면 추측하지 않고 누락 상태를 표시한다.
- **검증**: 학습팩 import/export와 이미지 참조 회귀.
- **상태**: 부분 해결. HWP·특수 PDF·Windows 선택 추출기 의존성은 별도 환경 검증 필요.

### 14-1. 학습팩에는 이미지 참조가 있지만 실제 자산이 없어 화면에 표시되지 않음

- **증상**: XML·문항에는 이미지 이름 또는 경로가 남아 있었지만 tpack 안에 원본 이미지가 없어 가져온 뒤 빈 이미지가 되거나 파일명만 보였다.
- **원인**: 문서에서 추출한 이미지의 해시·MIME·상대 경로를 manifest에 기록하는 단계와 실제 binary asset을 팩에 넣는 단계가 원자적으로 묶여 있지 않았다.
- **해결**: 이미지 후보를 만들 때 자산을 함께 저장하고 manifest의 참조를 팩 내부 경로로 정규화한다. 자산이 없거나 해시 검증이 실패하면 문항을 완성된 이미지 문항으로 표시하지 않는다.
- **검증**: 이미지가 있는 팩과 이미지가 누락된 팩의 import/render 회귀. 누락 팩은 오류 상태를 반환한다.
- **상태**: 부분 해결. HWP·특수 PDF·Windows 선택 추출기에서의 실제 이미지 추출은 별도 검증이 필요하다.

## Windows·CI·패키징

### 15. Windows SQLite 읽기 핸들·DPAPI·업데이트 임시 파일 문제

- **증상**: Windows에서 읽기 전용 DB 파일이 삭제/교체되지 않거나 보호 저장소 테스트와 업데이트가 실패했다.
- **원인**: 파일 핸들을 닫지 않은 상태에서 교체했고 Windows 보호 저장소와 macOS Keychain 분기가 같은 fixture를 사용했다.
- **해결**: 읽기 연결과 companion DB 핸들을 닫고, Windows DPAPI와 macOS Keychain 테스트를 분리했다. 업데이트 임시 파일 핸들도 닫은 뒤 교체한다.
- **검증**: Windows CI 독립 실행 파일·SQLite·DPAPI·업데이트 회귀.
- **상태**: CI 해결. 실제 개인 Windows GUI·알림 영역·코드 서명은 미검증.

### 16. GitHub Actions가 10분 이상 실행되거나 macOS job이 취소

- **증상**: 전체 테스트 매트릭스가 오래 걸리고 새 push가 이전 실행을 취소했다.
- **원인**: OS·기능별 job을 병렬 실행하지만 일부 Windows sync/study job은 전체 회귀를 포함해 오래 걸렸다.
- **해결**: 기능별 job과 standalone/Rust/server job을 분리하고 긴 job도 결과를 끝까지 기록하도록 했다.
- **검증**: 최신 run `44661314162`에서 macOS/Windows 24개 job 성공.
- **상태**: 기능상 해결. CI 전체 실행 시간을 더 줄이는 것은 별도 최적화 과제다.

### 16-1. Windows에서 보조 앱 경로 테스트와 시험 시간 불변식이 흔들림

- **증상**: Windows 경로 구분자 때문에 보조 앱 watcher 명령 테스트가 실패했고, 시험 제출 직후 타이머 테스트가 1초 차이로 실패했다.
- **원인**: 테스트가 POSIX 경로 문자열을 직접 비교했고, 제한 시간 검증에서 `remaining + overtime`을 경과 시간으로 오해했다.
- **해결**: 경로는 `Path.name`으로 비교하고, 타이머는 `remaining + elapsed = max(elapsed, limit)` 불변식을 검증한다. 런타임 타이머 계산은 변경하지 않았다.
- **검증**: 관련 로컬 38개 통과, 최신 Windows·macOS 전체 24개 CI job 통과.
- **상태**: 해결.

### 17. Windows 무설치 번들의 한국어 도움말이 출력되지 않음

- **증상**: Windows CI에서 `turtleneck.exe --help`가 한국어 도움말을 파일로 쓰는 순간 `UnicodeEncodeError`로 종료했다.
- **원인**: PyInstaller로 묶인 프로세스의 표준 출력 인코딩이 Windows 기본 `cp1252`로 남아 있었다. `PYTHONIOENCODING`만 설정해도 번들 시작 후의 스트림 설정을 보장하지 못했다.
- **해결**: 번들 진입점에서 표준 출력·오류 스트림을 UTF-8과 대체 문자 정책으로 재설정했다. CI에 CLI 도움말 실행과 보조 앱 `--status` 실행을 추가하고, 상태 JSON에 비밀번호·쿠키·세션·토큰 문자열이 없는지도 검사한다.
- **검증**: 로컬 ASCII 출력 환경 재현, 최신 CI `44054592665`의 macOS·Windows standalone job 성공.
- **상태**: 해결. 실제 사용자 PC의 시스템 로캘 전체 조합과 GUI 글꼴은 별도 실기기 검증이 남았다.

### 22. 공개 릴리스가 있는데 업데이트 확인이 최신 버전을 놓침

- **증상**: 공개 GitHub 릴리스는 `v0.6.4`였지만 `turtleneck` 브랜치의 `plugin.json`은 `0.6.2`라서, 브랜치 메타데이터만 읽는 설치본이 업데이트 가능 상태를 `CURRENT`로 잘못 판단할 수 있었다.
- **원인**: 업데이트 확인 버전과 실제 다운로드·체크섬 검증에 사용하는 릴리스 태그의 기준이 달랐다.
- **해결**: GitHub Releases API의 `tag_name`을 최신 버전의 기준으로 우선 사용하고, API를 사용할 수 없을 때만 브랜치 `plugin.json`으로 fallback한다. 실제 적용 단계에서는 릴리스 태그와 다운로드 체크섬이 계속 일치해야 한다.
- **검증**: 오래된 브랜치 버전과 `v0.6.4` 릴리스 태그를 함께 둔 fixture에서 `UPDATE_AVAILABLE`과 `remoteVersion=0.6.4`를 확인했고, 업데이트 검사 9개 및 macOS·Windows CI 전체를 통과했다.
- **상태**: 해결. 최신 릴리스와 브랜치 메타데이터의 버전 통일은 다음 패치 릴리스에서 별도로 관리한다.

### 23. 릴리스 dry-run이 태그·runner·패키지 경로 차이로 실패

- **증상**: `v0.6.4` 태그를 대상으로 한 첫 dry-run에서 Windows 번들의 한국어 도움말이 실패했고, `macos-14` arm64 job은 runner 할당 전에 취소됐다. macOS 패키지 검사도 ZIP 내부의 `_internal/` 경로 때문에 실패했다.
- **원인**: 기존 태그에는 Windows UTF-8 보정 전 코드가 남아 있었고, GitHub runner label이 현재 환경에서 더 이상 안정적으로 할당되지 않았다. PyInstaller onedir는 버전에 따라 자산 앞에 `_internal/`을 붙일 수 있는데 검사가 고정 경로를 가정했다.
- **해결**: 현재 `turtleneck` 브랜치의 수정 코드를 별도 dry-run으로 검증하고, arm64 runner를 `macos-15`로 변경했다. ZIP 검사는 절대 경로가 아니라 거북이 자산의 경로 suffix를 확인하도록 보정했다. 수동 dry-run은 `publish=false`를 기본값으로 해 GitHub Release를 만들지 않게 했다.
- **검증**: 현재 브랜치 기준 release dry-run `44069595150`에서 macOS Intel/ARM, Windows unsigned bundle, companion, source archive와 checksum 생성이 모두 성공했다. 첫 실패 run `44068668890`은 실패 원인을 기록하기 위한 시도이며 성공 수치에 포함하지 않는다.
- **상태**: 해결. 기존 `v0.6.4` 태그 자체는 수정하지 않았으므로 해당 태그를 다시 빌드할 때는 구형 코드의 결과가 재현될 수 있다.

### 24. Git이 없는 새 컴퓨터에서 설치가 시작되지 않음

- **증상**: Codex·Claude Code·Gemini에 GitHub 저장소 주소를 직접 넘기는 설치 명령이 내부 Git 호출에서 실패했다.
- **원인**: 호스트의 원격 마켓플레이스 설치 경로만 안내하고, 호스트가 지원하는 로컬 폴더 설치 경로를 사용하지 않았다.
- **해결**: Git이 있으면 기존 공식 경로를 유지하고, 없으면 현재 압축 해제 폴더를 로컬 원본으로 사용한다. 현재 폴더가 없을 때만 GitHub API로 공개 브랜치의 커밋 SHA를 확인하고, 해당 SHA에 고정된 ZIP을 임시로 받아 크기·경로를 확인한 뒤 로컬 설치하고 삭제한다.
- **검증**: 설치 스크립트 회귀 4개, macOS·Windows GitHub Actions `44206034909` 전체 성공. Windows 경로 구분자도 별도 확인했다.
- **상태**: 코드 경로 해결. Git·Python이 모두 없는 깨끗한 실기기에서의 실제 호스트 설치는 아직 미검증이며, 호스트 CLI 자체는 별도 설치가 필요하다.

### 25. 최초 로그인 폼이 서버 검증 전에 완료로 보일 수 있음

- **증상**: 저장된 비밀번호가 없는 첫 연결에서 입력을 받자마자 폼이 성공 화면을 표시할 수 있었다. 실제 TLS 로그인과 보호 저장소 저장이 뒤에서 실패하면 사용자는 등록이 끝난 것으로 오해할 수 있었다.
- **원인**: 재인증 시도에만 `submit_check`를 연결하고 최초 입력에는 연결하지 않았다.
- **해결**: 최초 입력도 로그인 검증과 보호 저장소 저장을 통과해야 폼이 완료 화면을 표시하도록 통합했다. 세션 복구 중 계정 표식이 없는 예외 경로도 안전하게 종료하도록 보정했다.
- **검증**: 인증·세션·보안 경계·설정·연결 표적 테스트 31개 통과.
- **상태**: 해결. 실제 학교 계정의 잘못된 비밀번호·보호 저장소 잠금 화면은 실서버 검증이 필요하다.

### 26. macOS Keychain 접근 때마다 별도 암호 확인이 반복됨

- **증상**: 로그인 세션을 재사용하는데도 TLS·에타·API 토큰을 읽을 때마다 `/usr/bin/security` 접근 확인이 반복될 수 있었다.
- **원인**: 저장은 현재 프로세스의 macOS Security API로 했지만 읽기는 매번 별도 `security` 프로세스를 실행했다. Keychain의 접근 주체가 달라져 저장된 항목을 재사용하지 못하는 환경이 있었다.
- **해결**: macOS에서는 `SecKeychainFindGenericPassword`로 현재 프로세스가 직접 읽고, 항목이 없는 기존·테스트 환경에서만 제한적으로 기존 CLI fallback을 사용한다. Everytime 세션과 Canvas/Moodle API 토큰도 같은 읽기 경로를 사용하며, 비밀값은 파일·로그·모델 출력으로 복사하지 않는다.
- **검증**: 인증·프로필·Everytime·Canvas·Moodle API 표적 테스트 36개 통과. 실제 Keychain 접근 승인 정책에 따라 최초 1회 OS 확인은 남을 수 있다.

### 27. 세션 재사용 때에도 키체인 암호 확인이 반복될 수 있음

- **증상**: 비밀번호 저장 경로는 네이티브 API였지만, 저장된 TLS 세션 쿠키를 읽을 때는 `/usr/bin/security`를 별도 실행해 macOS 확인 창이 다시 나타날 수 있었다.
- **원인**: 세션 읽기만 이전 호환용 CLI fallback을 직접 호출해 현재 프로세스와 다른 접근 주체로 키체인 항목에 접근했다.
- **해결**: 세션 쿠키도 비밀번호와 같은 네이티브 `SecKeychainFindGenericPassword` 경로를 사용하도록 통일했다. 만료 세션 삭제와 중복 항목 교체도 네이티브 삭제 경로를 사용하며, CLI fallback은 기존 항목 마이그레이션이 필요한 경우에만 제한적으로 남겼다.
- **검증**: TLS 로그인 표적 테스트 19개 통과. 세션 저장·복원·만료 정리 테스트에서 별도 `security` 읽기·삭제 호출 없이 보호 저장소 helper를 사용한다.
- **남은 위험**: macOS가 앱 서명·터미널·Python 실행 주체를 새로 인식하는 최초 승인, 사용자가 키체인 접근을 취소한 경우의 재승인은 운영체제 정책상 남을 수 있다.
- **상태**: 코드 해결. 깨끗한 macOS에서 최초 승인 후 재실행 시 추가 암호 확인이 없는지 실기기 검증이 필요하다.

### 28. 키체인 접근 실패가 반복 승인 창으로 되돌아감

- **증상**: 현재 프로세스의 네이티브 Keychain 접근이 실패하면 매 실행마다 `/usr/bin/security` fallback이 호출되어 macOS 승인 창이 반복될 수 있었다.
- **원인**: 이전 항목 마이그레이션을 위해 남겨둔 CLI fallback이 일반 읽기 경로에서도 동작했다.
- **해결**: 일반 읽기에서는 CLI fallback을 사용하지 않는다. 오래된 항목은 명시적인 연결 절차에서 다시 저장한다. 비밀값은 계속 OS 보호 저장소 밖으로 나가지 않는다.
- **검증**: 네이티브 접근 오류 시 CLI가 호출되지 않는 회귀 테스트와 TLS 로그인 19개를 통과했다.
- **남은 위험**: 실행 파일 경로가 바뀌거나 사용자가 키체인 접근을 취소하면 운영체제 정책상 한 번의 재연결이 필요할 수 있다.

### 29. 키체인 승인을 매번 직접 입력해야 하는 사용성 문제

- **증상**: 같은 터틀넥을 다시 실행해도 macOS가 보호 저장소 접근을 새 앱처럼 확인하거나, 사용자가 매번 암호를 입력해야 했다.
- **원인**: 저장 시 키체인 항목에 현재 실행 파일을 신뢰 앱으로 명시하지 않아 실행 주체가 바뀔 때 ACL 확인이 반복될 수 있었다.
- **해결**: 저장 시 현재 실행 파일 하나만 신뢰하는 ACL을 설정한다. 모든 앱을 허용하는 빈 목록은 사용하지 않으며, 일반 읽기 경로에서 CLI `security` fallback도 호출하지 않는다.
- **검증**: 신뢰 대상이 현재 실행 파일 하나인지 확인하는 회귀 테스트를 추가했다. 실제 macOS 키체인 승인 창은 깨끗한 실기기에서 한 번 선택해야 한다.
- **남은 위험**: Python·보조 앱·서명된 번들의 실행 파일이 서로 다르면 각 실행 주체에 대해 최초 1회 확인이 남을 수 있다.

### 30. 키체인 일반 조회가 OS 승인창을 다시 띄울 수 있음

- **증상**: 접근 ACL이 오래됐거나 실행 파일이 바뀐 환경에서 일반 동기화가 macOS 키체인 암호창을 반복해서 보여줄 수 있었다.
- **원인**: 네이티브 조회가 권한 확인을 위해 운영체제 상호작용을 허용한 상태로 실행됐다.
- **해결**: 일반 조회 중에는 `SecKeychainSetUserInteractionAllowed(false)`로 OS UI를 차단하고, 권한이 없으면 즉시 연결 절차로 돌린다. 명시적 재연결·마이그레이션 저장 때만 상호작용을 허용한다.
- **검증**: UI 차단·복구와 CLI fallback 금지 회귀를 포함한 프로젝트 40개, TLS 로그인 19개 표적 테스트 통과.
- **남은 위험**: 최초 저장·명시적 재연결 때의 OS 승인은 macOS 정책상 한 번 필요할 수 있다.

### 31. 무설치 보조 앱에서 학교 로그인 메뉴가 본체를 실행하지 않음

- **증상**: Python 환경에서는 보조 앱의 `학교 로그인·연결`이 동작하지만, PyInstaller로 만든 보조 앱에서는 로그인 화면이 열리지 않을 수 있었다.
- **원인**: 보조 앱이 `sys.executable`을 그대로 사용해 자기 자신에게 `setup_turtleneck.py` 경로를 넘겼다. 무설치 보조 앱은 본체 실행기와 별도 파일이라 이 인자를 해석하지 못하고 종료했다.
- **해결**: 시험지 열기와 같은 방식으로 인접한 본체 번들, PATH의 본체 실행기, 현재 실행기를 순서대로 찾고 본체에 로그인 준비 스크립트를 전달하도록 수정했다.
- **검증**: macOS 번들 경로 모의 회귀와 보조 앱 테스트 8개를 통과했고, 수정본을 로컬 설치본에도 반영했다.
- **상태**: 코드 해결. 실제 Windows 알림 영역 번들에서 로그인 버튼을 누르는 실기기 검증은 남아 있다.

## 생성·학습 흐름과 사용자 경험

### 18. 20문항 생성이 17분, 문제은행 생성이 약 1시간 이상 걸림

- **증상**: 자료구조 20문항 요청이 17분, 대량 문제은행 생성이 약 1시간 6분 걸렸다. 중간에 무엇이 끝났는지 알기 어려웠고 같은 자료를 다시 분석하는 것처럼 보였다.
- **원인**: 파일 추출, 파일별 후보 생성, 문항 조립, 검수 단계가 하나의 긴 작업처럼 실행됐다. 파일 후보·개념 분석·이미 생성된 문항을 재사용하는 경계가 약했고, AI 호출과 로컬 변환의 시간이 구분되어 보이지 않았다.
- **해결**: 파일 단위 분석 결과와 문항 후보를 로컬 기록으로 저장하고, 이미 검증된 후보는 다시 분석하지 않는다. 생성된 문항은 준비되는 순서대로 시험지에 전달하며 단계별 상태를 표시한다. 범위를 먼저 확인하고 선택 파일만 처리한다.
- **검증**: 캐시 재사용·부분 생성·재시험·웹 전달 회귀와 study-generation benchmark를 통과했다.
- **상태**: 부분 해결. 실제 저성능 모델·20문항·대량 문제은행의 목표 시간과 AI 제공자별 평균은 아직 확정하지 않았다.

### 19. 강의 개요·일정이 공지나 Q&A와 함께 수집되지 않음

- **증상**: 교수님이 별도 개요 영역이나 토픽 설명에 적은 시험 일정·범위가 공지 검색 결과에 없어서 일정이 빠졌다.
- **원인**: 공지 게시판과 Q&A만 우선 조회하고 Moodle section overview/활동 설명을 동일한 학업 정보로 정규화하지 않은 경로가 있었다.
- **해결**: 현재 수강 강좌의 section overview와 활동 설명을 별도 수집 대상으로 두고, 날짜·범위가 실제로 보일 때만 일정 후보로 저장한다. 날짜가 없으면 임의로 계산하지 않는다.
- **검증**: section overview parser와 실제 9과목 fixture 동등성 검사를 통과했다.
- **상태**: 부분 해결. 학교별 커스텀 테마에서 개요가 다른 위치에 렌더링되는 경우는 Moodle adapter별 확인이 필요하다.

### 20. 예제 시험지 화면이 실제 시험지와 달라 사용자가 혼란을 느낌

- **증상**: 설치 없이 보는 예제 페이지가 실제 로컬 시험지의 문제 표시·시작 전 잠금·이미지·제출 상태와 달랐다.
- **원인**: 예제용 정적 화면과 실제 `exam_web.py` 계약이 별도로 발전했고, 예제 화면을 실사용 UI의 검증 대상으로 취급하지 않았다.
- **해결**: 실제 시험지의 시작 전 문제 잠금, 문항 이미지, 저장·제출 상태, 재시험 흐름을 기준 계약으로 삼고 예제는 동일 자산·동일 상태 전이를 사용하도록 맞춘다.
- **검증**: 실제 로컬 시험지의 브라우저 회귀는 일부 확인했지만, 공개 예제 페이지와의 픽셀·접근성 비교는 아직 완료하지 않았다.
- **상태**: 미해결. 공개 배포 전 예제 페이지를 실제 시험지와 다시 대조해야 한다.

### 21. 과제 제출 기능이 “제출 완료”처럼 보일 위험

- **증상**: 과제 초안·파일 준비와 실제 TLS 제출이 혼동될 수 있고, 사용자가 제출 파일 주소와 최종 확인 결과를 한 번에 받지 못하는 흐름이 있었다.
- **원인**: 과제 조건 확인, 파일 생성, 업로드 POST, 제출 결과 재조회가 한 계약으로 분리되어 있지 않았다.
- **해결**: 제출 전 교수님 조건·댓글·사용자 추가 확인을 거치고, 업로드 성공과 제출 상태 재조회가 모두 성공한 경우에만 제출 완료로 표시한다. 실패 시 파일은 로컬에 보존하고 제출 완료로 기록하지 않는다.
- **검증**: 제출 양식·중복 제출 방지·최종 상태 확인 fixture를 통과했다.
- **상태**: 부분 해결. 실제 강좌에서의 제출 POST와 교수 화면 확인은 실행하지 않았다.

### 32. TLS 개요에만 있는 외부 과제가 일반 과제 목록에서 빠짐

- **증상**: 클라우드컴퓨팅의 DataCamp 과제가 TLS 과제 활동으로 등록되지 않아 과제 목록만 보면 누락될 수 있었다.
- **원인**: 외부 서비스 안내는 `tls-overview` 공지로 저장되지만, 일일 보고서는 TLS assignment와 강의만 표시했다.
- **해결**: 외부 URL·DataCamp·외부 과제/퀴즈 안내가 포함된 강의 개요를 `외부 학습 안내`로 표시한다. TLS 내부 과제로 추정하거나 제출 완료로 만들지 않는다.
- **검증**: 전용 회귀 테스트와 전체 회귀 테스트를 통과했다.
- **남은 위험**: URL이나 외부 서비스명이 없는 자유 서술형 안내는 자동 감지하지 못할 수 있어 원문 개요 확인이 필요하다.

### 33. 잘못된 HTTP Range 응답이 부분 파일에 붙을 수 있음

- **증상**: 중단된 대용량 파일을 이어받을 때 서버가 형식은 맞지만 시작·끝·전체 크기가 서로 맞지 않는 `Content-Range`를 보내면 기존 부분 파일 뒤에 잘못된 바이트가 붙을 가능성이 있었다.
- **원인**: 시작 위치만 확인하고 끝 위치와 `Content-Length`의 일치를 검증하지 않았다.
- **해결**: Range 응답의 시작·끝·전체 크기와 남은 본문 길이를 모두 검증하고, 범위가 비정상이면 파일에 쓰기 전에 중단한다. 기존 부분 파일은 보존해 재시도 판단에 사용한다.
- **검증**: 정상 Range 재개, 짧은 응답 후 재개, 잘못된 범위 무쓰기 회귀를 통과했다.
- **상태**: 코드 해결. 실제 학교 미디어 서버가 보내는 장시간 Range 응답은 별도 측정이 필요하다.

### 34. 음성 전용 HLS가 없는 강의가 전부 제외됨

- **증상**: 실제 완료 강의 37개를 다운로드 없이 확인했을 때 모두 `음성 전용 스트림 없음`으로 제외됐다.
- **원인**: HLS 마스터에 오디오 전용 playlist가 없고 일반 영상 variant만 있는 경우를 트래픽 보호를 위해 무조건 거부했다.
- **해결**: 사용자가 이미 시청 완료한 강의에 한해 가장 낮은 비트레이트 영상 variant를 선택하고, 로컬에서 화면을 제거해 음성을 추출한다. 음성 전용 variant가 있으면 기존 우선순위를 유지한다.
- **검증**: 실제 TLS 완료 강의 37/37의 재생 주소·제한·playlist 확인 성공, 그중 1개는 197개 조각을 스트리밍 저장·음성 변환·로컬 저장까지 완료했다. 재실행은 로컬 음원을 재사용했고 7개 요청·64,790B만 발생했다.
- **남은 위험**: 실제 강의별 오디오 트랙 존재·전사 정확도와 장시간 중단 후 재개는 개별 파일 특성에 따라 추가 확인이 필요하다.

### 35. 미디어 서버 대기 신호 뒤 후보 스트림을 계속 조회함

- **증상**: 재생목록 요청이 일시적으로 실패하면 같은 강의의 다른 후보 주소를 계속 시도해 확인 시간이 길어질 수 있었다.
- **원인**: 서버 대기 신호인 `RequestBackoff`가 일반 URL 오류처럼 처리돼 후보 순회에 흡수됐다.
- **해결**: `RequestBackoff`는 즉시 상위 흐름으로 전달해 추가 후보 요청을 막고, 다음 실행에서 서버 대기 정책을 따르게 했다.
- **검증**: 후보 순회 중 대기 신호가 발생하면 첫 후보에서 중단하는 회귀 테스트와 미디어 전체 34개 테스트를 통과했다.
- **상태**: 코드 해결. 실제 서버의 오류 응답 분포와 평균 지연은 별도 측정이 필요하다.

## 재발 시 점검 순서

1. `git log -1`, GitHub Actions run, 로컬 설치본의 커밋이 같은지 확인한다.
2. 로그인 폼이 반복되면 보호 저장소의 빈 값, 세션 만료, `.auth` 잠금 대기를 확인한다. 비밀번호·쿠키·세션 값은 로그에 남기지 않는다.
3. 동기화가 오래 걸리면 범위, 캐시 TTL, 재시도 대기, 실제 요청 수를 확인한다. 실패한 자료를 완료로 표시하지 않는다.
4. 큰 파일이면 `.partial`·manifest·파일 크기 제한·Range 응답을 확인한다.
5. 실서버 측정이 실패하면 기존 성공 기록을 덮어쓰지 않고 `live-attempt.json`만 확인한다.
6. 오류 코드와 로컬 redacted report만 공유한다. 비밀번호·쿠키·세션·토큰·서명 URL·원본 자료는 공유하지 않는다.
7. 문제은행이 오래 걸리면 AI 호출 횟수보다 먼저 캐시 적중 여부, 파일별 후보 수, 현재 단계, 남은 범위를 확인한다. 이미 완료한 파일을 다시 분석하지 않는다.
8. 학습팩에서 이미지가 안 보이면 화면 경로가 아니라 팩 manifest의 asset 존재·해시·MIME·상대 경로를 먼저 확인한다.
9. “완료” 문구는 파일 생성·원격 반영·결과 재조회가 모두 끝난 경우에만 사용한다. 준비·업로드·확인은 서로 다른 상태다.
